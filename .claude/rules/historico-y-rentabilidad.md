# Histórico del patrimonio y cifras de rentabilidad

#### The imported portfolio can now carry its ledger, and the history window is decided by the data (10-ago-2026)

Two halves of one thing: a CSV with dates has everything needed to rebuild the past, and both the ledger and the reconstruction window were throwing it away.

- ⚠️ **Every transactional parser built a `transactions` array and dropped it.** They all raise one to feed `reduceTransactionsToPositions()` and keep only the consolidated result, so `importFromCSV` returned positions and the dates died there. Consequence: an imported portfolio is born in manual mode, **`fiscal.ts` cannot apply FIFO so the whole IRPF panel is off**, and the reconstruction cannot go backwards because `sharesAt()` does not know the past share counts and assumes today's. `ImportResult.transactions` now carries them (in the importer's own shape — `Date`, `BUY`/`SELL` — which is a different type from `$lib/types`).
- **`src/lib/importers/ledger-import.ts` decides which assets may enter with a ledger**, out of the component because it decides whether the portfolio shows the right number of shares. ⚠️ `effectiveHoldings` **prefers the ledger** over manual holdings, so an incomplete ledger means showing less than the user owns — going from *correct without history* to *with history and wrong*, which is worse because it is unnoticeable. Three conditions, and the first is the one that matters: **a sale with no purchases behind it**, which is what happens whenever somebody downloads only the last twelve months. ⚠️ Comparing the net against the position detects nothing there — the position was computed *from those same operations*, so it always ties. Also excluded: operations outside the base currency, because the ledger stores an `fxRate` per operation and the CSV does not carry the rate **of each purchase day** — writing `fxRate: 1` on a dollar asset does not leave the cost approximate, it leaves it wrong by however much the pair has moved.
- ⚠️ **`HISTORY_DAYS = 30` said "limited by what Yahoo's sparkline gives" and that was false.** `/api/prices` already asked Yahoo from 20 December of the previous year — `calculateHistoricalMetrics` needs that for YTD — so between 160 and 250 closes arrived and **all but the last 30 were discarded one line later** by a `slice(-30)`. The limit was ours. Now `diasDeHistorialPedidos()` (in `priceHelpers.ts`, because SvelteKit forbids arbitrary exports in a `+server.ts`) serves what is asked for via `?historyDays=N`, the Redis key moved to `price_history_v2:` because what is cached changed shape (full series, trimmed on the way out), and `PortfolioStore.ventanaHistorica` derives the window from **the oldest date the ledger or the edit log knows**, floored at 30 and capped at 400.
- ⚠️ **Why not just serve the long series always**: that array travels inside the prices response, which the client polls **every 30 s** — 250 points across nine assets is ~20 KB extra per response, megabytes per hour for data that does not move during a session. So it is requested once per ticker set. And ⚠️ **`this.prices = data.prices` replaces wholesale**, so without merging, the long series arrived on load and the first poll shrank it back to 30: the chart would shrink by itself thirty seconds later with no error anywhere. `performanceSeries.test.ts` pins that with two sequential `fetchPrices()`.
- ⚠️ **Widening the window without a ledger would make things worse, not better.** Past share counts come from the ledger or the edit log; with neither, `sharesAt()` returns today's for the whole past and flags it `estimated` — the very stretch that was excluded from the return figures for contaminating them. Hence the window follows the data instead of a constant.
- ⚠️ **And the fix above was incomplete: `period1` stayed anchored to 20 December of the previous year.** The output trim was widened and the *request* was not, so asking for `?historyDays=400` returned **149 points** — measured against production after deploying. The reconstruction was capped at about seven months no matter how far the ledger reached, and it looked like it worked because 149 is still far more than 30. ⚠️ **The same anchor carried a seasonal bug that had been there from the start and only shows up on one date: every 1 January the whole history collapses to two weeks**, because the anchor moves to the December just gone. Same class of defect as the one `calculateHistoricalMetrics()` takes `now` for. `period1` is now the older of the two — the 20 December anchor, needed to hold the previous year's last close for YTD, or the start of the requested window. Asking for more days bothers no calculation: the metrics search their three cutoffs inside the series, and the trim happens on the way out. `SPARKLINE_DIAS_MAX` also went 400 → **550** (≈18 months), because a 13-month ceiling should not be what truncates somebody contributing for a year and a half — the asset's own coverage should be.
- ⚠️ **The gap before the asset's price series is now filled with the shape of its index, not with a flat line.** The flat fill asserted **0 % variation** across whole months — on the case that motivated it the market moved about 10 %, so that was the error being carried. `alignPriceSeriesWithProxy()` drags the gap with `primer_precio_real × (proxy(d) / proxy(día_del_ancla))`, so the splice point matches the first real price **exactly** (no step at the join) and only the *shape* is borrowed, never the level — a proxy trading at 95 € and a fund at 12 € give the same curve. ⚠️ **`paddedBefore` deliberately does not shrink**: it is what marks the stretch as estimated, and a stretch rebuilt from an index is still an estimate — improving the number does not make it an observation. `PerformanceSeries.reconstructedWithIndexDays` counts those days so the notice can say *what* it was rebuilt from; it travels in the series and not as store `$state` because **writing state inside a `$derived` is forbidden in runes** (`state_unsafe_mutation`) — the first attempt did it and ten tests caught it at once.
- **`indices.json` gained `priceProxy` on five indices** (World, All-World, S&P 500, Emerging, World Small Cap), read through `priceProxyOf()`. ⚠️ They are **ETFs quoted in euros, not the indices**: indices publish in dollars, and dragging a euro fund with a dollar series injects the period's EUR/USD move — 5-8 % over six months, more error than the fix removes. TER and tracking difference stay inside the accepted error (0,12 % a year is 0,06 % over six months). Verified against Yahoo 10-ago-2026: all five answer in EUR with ~915 closes since 2023, well past the 550-day ceiling. An index **without** a proxy is not filled at all — the chart starts where real data starts, which beats inventing it flat. The full reasoning lives in `priceProxyNote` inside the JSON.
- **The proxies ride along in the same prices request** (`proxyTickers`), per *index* rather than per asset, so three World funds share one request and one cache entry. They are kept out of `allUserTickers` on purpose: a proxy is not a position and must not show up in the portfolio with its own weight and drift. ⚠️ **And the test that matters is the one that nearly did not exist**: four tests covered the `proxyTickers` derived value and its negative control showed **none of them noticed when the proxies stopped travelling in the request** — the derived value would stay correct, the splice would get no prices, and the chart would silently fall back to the flat fill. There is now a test on the request URL itself.
- ⚠️ **The estimated-stretch notice had gone false and there are two now.** It said "assuming you already held those shares before the app started recording changes", and with a ledger the app **does** know the share counts for each day — what it lacks is the NAV. `chart_estimated_note_index` says what the stretch was rebuilt from, because an estimate with no stated provenance is indistinguishable from data.
- **Measured, and it caps what this can ever show**: Yahoo has **229 daily closes for `0P0001XF40.F` starting 2025-08-26** against a first contribution of 2025-02-10, and 515+ for `IWDA.AS`. So depth is limited by two independent things — ledger reach *and* each asset's price series — and the second varies per asset, which `paddedBefore` already marks. Note those two tickers are the ones in `RELIABLE_FT_MAPPINGS`.
- **Verified in the browser with a real 25-lot file**: 2 assets imported, both with ledger, and the prices request carrying `historyDays`. ⚠️ **What was NOT verified on screen**: the chart itself drawing more than 30 days — the harness kept failing to reach `.history-section` behind the dashboard tabs and it was dropped rather than chased, per the rule already written here about browser rabbit holes. The mechanism is covered by unit tests instead (a 90-day-old transaction yields 91 points; a short poll does not shrink it).

#### The two return figures did not match the chart they sit next to (10-ago-2026)

Four defects behind one complaint — *«no casan el gráfico de evolución del patrimonio con lo del coste del timing»*. All four were arithmetic or labelling, none was visible in a screenshot; they came out of reading `performance.ts` against `HistoryChart.svelte` and then **running the pure modules to get numbers**.

- ⚠️ **The two returns included the *estimated* days.** `reconstructDailySeries` flags `estimated: true` the days it cannot really see and fills them with an estimate; the chart honours that — draws them differently and warns — while `twrPeriod`/`mwrPeriod` folded them into the arithmetic in silence. Measured: with two estimated days at the front, the period TWR went from a real **2,00 %** to **13,33 %** — eleven points of invented return, in the figure the UI presents as "what your assets returned". They now start at `firstMeasuredIndex`, which **already existed and already had tests**: what was missing was anyone reading it. A fully estimated window returns `0`/`null` so the panel switches off instead of inventing a figure, and `TimingCost.svelte` now decides `hasFlows` over the measured stretch too — a contribution landing in the estimated days can no longer enable a comparison that does not include it.
- ⚠️ **TWR and MWR dated the flows one day apart, and their difference is the headline.** `twrIndex()` counts an inflow at the **start** of its day (`base = begin + inflow`); `moneyWeightedReturn()` placed it at `i / span`, the **close**. So the two metrics measured different exposures and the gap the UI calls "the cost of your timing" carried a residue that was not timing. Not negligible: with `[1000, 2000 (+1000), 1800]` — contribute, then eat the whole following drop, no calendar decision to judge — it produced an MWR *worse* than the TWR, i.e. a fabricated penalty. `flowTime()` aligns them, and both give −10 %. ⚠️ **The test that covered this was passing on floating-point noise**: with the convention aligned its assertion (`mwr < twr`) survives on a bisection error of **−3,2e−13**. It was rewritten with the shape where timing genuinely exists — money in after a good stretch and before a bad one — which measures **−5,57 pp**, and gained a mirror case (**+6,42 pp** for contributing after a fall) plus a test that pins the convention itself.
- ⚠️ **`YTD` and `Todo` never warned that they show a month, and `Todo` is the default range.** The series cannot exceed `HISTORY_DAYS` (30) because the reconstruction lives off Yahoo's sparkline, and `overlaySnapshots` is a `points.map()` — it fills gaps inside the window, it does not lengthen it. So every saved snapshot older than a month is unreachable, and the old predicate (`days !== null && points.length < days`) skipped exactly the two ranges whose `days` is `null`. The decision now lives in **`src/lib/history/range.ts`**, out of the component, for the usual reason: it decides something. It distinguishes two situations that were being conflated — `short` ("you haven't been here that long", nothing is missing) from `capped` (there *is* older history the reconstruction cannot reach), because `short`'s wording asserts there is no more data and in the second case there is. `PerformanceSeries.oldestKnownDate` carries the fact the chart cannot know on its own. ⚠️ A range of N days is **today plus the N−1 before it** (what the `slice` draws), so `rangeStartDate` subtracts `days - 1`: with `- days` the requested date falls one day behind a full window and «1M» would warn *always* — a permanent warning, which this file elsewhere calls the failure mode to avoid. Its own test caught that.
- ⚠️ **`timing_period_note` said «Cifras del periodo mostrado» and that was false.** The figures are computed over the whole series while the chart slices to the selected range *and* rebases the TWR to its first visible day (`twrBase`). Measured on one series: **−4,05 %** in the panel against **−3,73 %** and **−1,79 %** for windows starting at day 10 and 20. With today's ranges that divergence is only reachable via `YTD` in January — narrow, but the sentence was wrong the moment you touched the selector. The note now declares the days it actually measured, which after the first fix matches no selector range by design.
- **What was checked and is *not* a defect**, kept because the next reader will suspect it too: the `Math.max(0, …)` in `investedSeries()` does not misattribute contributed capital to the market — the case built to force the clamp never triggers it, and the scenario that seemed to show it had impossible inputs (5.000 € of value on 400 € of cost). And `moneyWeightedReturn`'s `hasInflow || hasOutflow` guard is dead code rather than a bug: the opening value and the closing value always enter as flows, so both are always true, but `TimingCost.svelte` gates on its own `netFlow` check before any of it reaches the screen.
- **`TimingCost.test.ts` exists for the same reason as `TaxAwareRebalance.test.ts`**: verified in `vite preview` that the demo portfolio has no contributions or sales, so in a browser this panel *always* says «hace falta al menos una aportación», and the populated path was exercised nowhere. `performance.ts` and `range.ts` are both in the coverage ratchet now (94/90 and 100/95) — being outside it is how a figure the user reads as their own drifted eleven points.
- ⚠️ **`Projections.svelte` draws a scenario cone, and the single deterministic line it replaced was the politest lie in the app.** It said "in twenty years you will have 702.854,19 €" when it meant "if you hit 7 % on each of 240 consecutive months, this is what falls out". No year returns its mean. `src/lib/montecarlo.ts` runs a seeded Monte Carlo (600 paths) and returns p10/p25/p50/p75/p90 per year; the seed is fixed for the same reason `calculateTaxAwareRebalance()` takes `now` — without it there is no test, and a chart that reshapes itself when you move an unrelated slider reads as broken. ⚠️ **`annualReturn` is the MEDIAN, not the arithmetic mean**, which is what makes the central line compound at exactly the rate the slider says; a property test pins it. Volatility is a **visible control, not a hidden constant**, because the width of the cone is the user's assumption exactly as much as the return is, and burying it would be selling an invented figure as data again. On the dark ground the *more* probable ribbon is the *lighter* one — the comment in the markup said the opposite until the render was actually looked at.
- **`Projections.svelte` previously drew an SVG stacked area, not 21 CSS bars.** The bars stacked `invested` *above* `profit` (first child of a `flex-direction: column` is the top one), had no axis, legend or tooltip, and used translucent fills — the exact thing `DeviationTreemap.test.ts` has a test to forbid. The two fills are **two steps of one blue** rather than two hues, because contributed capital and growth are parts of one total, not competing categories; the dark step is at 2,89:1 against the surface, under 3:1, which is why the legend carries labels and the three figures are stated in full above the chart.
- Font: Plus Jakarta Sans, **self-hosted** in `static/fonts/` with woff2 400/700 preloads.
- **The heavy visual effects were measured and are not a performance problem — don't "optimize" them away.** `.background-mesh` (`filter: blur(80px)`, 40px on mobile, plus a 25 s infinite `transform` animation), the full-viewport `.noise-overlay` (`feTurbulence`) and the card `backdrop-filter: blur()` were all suspected of hurting LCP and INP. `npm run measure:filters` on throttled mobile says otherwise: LCP sits around 600–700 ms — roughly a third of the 2.5 s "good" threshold — and **every** difference between having the effects and removing them came out smaller than the run-to-run noise floor, sometimes with the wrong sign. The animation costs nothing sustained either: median frame 16.7 ms and **zero** frames over 32 ms in every variant, because a `transform` animation on a filtered layer is composited. These are lab numbers; the deciding data would be real Speed Insights field metrics, which need the Vercel account.
- Dashboard tabs (`src/routes/dashboard/+page.svelte`): all tabs render **always** and are hidden with `class:tab-hidden` — deliberately no `{#if}` per tab, so Chart.js canvases don't remount and lose state. Don't "optimize" this into conditionals. Same applies to the two maps, whose region/sector toggle would reset on every tab change.
- ⚠️ **Two of the three donuts are gone, and the reason is that they were doing no work.** "Estrategia actual" and "Detalle Global" were the same assets with a different denominator, and past four slices nobody reads 13,02 % against 10,98 % off two arcs — they read it off the legend, which means the legend was the chart and the ring was decoration. Worse, the legend *couldn't* do the job either: `iShares Core MSCI World` and `iShares Core MSCI EM IMI` share an 18-character prefix, so both truncated to `iShares Core MS…` with **no `title`, no ticker and no tooltip** — two legend rows saying literally the same thing, and that is the normal case for the target user (iShares Core / Vanguard FTSE / Amundi Prime all pair like that). `CompositionBars.svelte` replaces both: ranked bars grouped by block, full names, and room for the thing a donut structurally cannot show — **the target**. The categories donut stays, because three slices is exactly where a donut is the right form, and it now carries the total in its hole (`cutout: '70%'` left 49 % of the area empty). Grid went from five lanes to four.
- **`src/lib/drift.ts` + `DriftChart.svelte` answer the one question no competitor answers: _how long have you been out of band?_** The deviation map answers it for today; this answers it for the last months, which is also the only way to see whether the rebalances you did actually achieved anything. Ghostfolio and Portfolio Performance show what you hold and what it returned — neither shows how long you have been off-target, because neither is a rebalancing tool. ⚠️ **Drift is measured inside the block, never over net worth**: targets are weights within `core`, so individual stocks rallying does not unbalance an 80/10/10 — it only makes core weigh less overall. Measuring over the total would invent a deviation every time an untargeted block moves; a test pins exactly that. Two more things it needs: `DailyPoint.byTicker` (the reconstruction already computed per-asset values and threw them away — the change is additive and the field is optional, because snapshot-derived points genuinely have no breakdown and a gap is more honest than a zero), and `driftAxisMax()`, which ⚠️ **must never scale below the band**: a perfectly on-target portfolio peaks at 0,2 pp, so scaling to the data would push a ±5 band off both ends of the canvas and draw the calmest possible portfolio as the most alarming one.
- ⚠️ **`isWithinBand()` exists because the exact edge of the band was decided by the sign of the rounding error.** A holding at 15 % against a 20 % target computes `0,15 − 0,2 = −5,000000000000002` pp and a bare `<=` calls it out of band, while the mirror case (`0,85 − 0,8` → 4,999999999999993) calls it in. Found by the boundary test in `drift.test.ts`; both modules now ask the same shared function, so they cannot answer differently.
- **`src/lib/composition.ts` is the pure half of that panel**, same split as `weights.ts` and `treemap.ts`. It carries `TOLERANCE_BAND_PP` — 5 points, the figure the project's own blog post already uses, **absolute not relative**: a 10 % target with a 5 pp band tolerates 5–15 %, not 9,5–10,5 %. ⚠️ `compositionScaleMax()` must consider the *targets* and not just the bars, because a heavily underweight asset puts its marker beyond every bar — and ⚠️ **the demo portfolio does not exercise that**: its worst case is covered by the 8 % headroom, so the first version of that test passed with the fix reverted. The test now uses a 40 %-actual-vs-80 %-target fixture. `CompositionBars.test.ts` covers the wiring the pure tests cannot see (a tick and a band only on rows that have a target, band wrapping the marker, nothing escaping the track).
- **The bar is the asset's colour; the state lives in position and in the number.** Whether you are inside the band is read from where the bar ends relative to the band rectangle, plus a signed figure in `pp` wearing the state colour and an arrow. Painting the bar amber would say "this asset is amber" and "this asset is high" with one channel.
- **`.charts-grid` was five lanes: three donuts and the two maps** (now four — see above). On mobile it is a scroll-snap carousel (`repeat(5, 100%)`), on desktop a fixed three-column grid — fixed columns rather than `auto-fit` precisely so that spans are predictable. **The look-through map used to span two of those three lanes, and that rule is gone**: it existed because the maps shared the grid with the donuts, where a single 400 px lane left a dead third column, and it stopped applying the moment the maps moved into their own folded row (see below). ⚠️ It is worth remembering how it failed before, because the same trap is still open for any span: the CSS comment and this file both claimed the rule for months while nothing implemented it. Whatever sets a span must also carry `:not(.is-wide)` — expanding sets `grid-column: 1 / -1` on the same property and has to win. Widening a map's lane also un-narrows the map itself, which is what turns on the region names inside its rectangles, since everything there derives from `contentWidth`. The maps live here rather than in a section of their own because as full-width cards they took two screenfuls of mobile scrolling; as carousel lanes they are two more swipes. Two consequences to keep in mind when adding a lane: every lane needs `align-self: start`, or the tallest one (the look-through map) stretches the donuts into a huge empty box; and that same map's footnotes are inside a `<details>`, and its mobile canvas is deliberately *not* square, for the same reason.
- ⚠️ **On desktop that grid is no longer three equal columns and the maps are no longer lanes of it — they are folded behind one line.** The complaint that started it was "too many charts in a row", and measuring four mockups said the height was not really the problem: deleting two panels only took ~13 % off, because a panel promoted to full width costs back most of what deleting its neighbour saved. What made the tab read as a wall was that **five panels carried exactly the same visual weight**, inside a glass card that was itself inside a glass card, under a third one for the history chart. So: `.charts-row-card` and `.history-section` drop their background, border, shadow and `backdrop-filter` above 1024 px (they keep them on mobile, where the frame is what gives the carousel lane an edge), the history chart is the one thing at full width, and composition / categories / drift share **one** row. The measured result on the same mockup was **−45 % of height**, the largest of the four options and the only one that deletes nothing.
- ⚠️ **The three lanes are `1.25fr 0.8fr 1.15fr` and the uneven split is load-bearing.** With three equal thirds the composition panel gets ~370 px and truncates fund names to `iShares Core MSCI W…` — which is the exact defect that killed the two donuts, reintroduced one layout later. At `1.25fr` it gets ~465 px on a 1440 px viewport and the names fit. Known and accepted cost: with a nine-asset portfolio the composition list runs ~420 px tall against ~200 for the donut, so the row's bottom edge is ragged. `align-self: start` stays (stretching would turn the two short lanes into huge empty boxes, which is the older lesson above).
- ⚠️ **The maps fold with CSS, never with `{#if}`, and `display: contents` is what keeps mobile intact.** `.maps-fold` wraps both maps plus the header button; folded, `.maps-fold:not(.is-open) .maps-row` is `display: none`, so the two panels **stay mounted** — unmounting would reset the look-through map's region/sector toggle, the same reason the tabs never use conditionals. Hidden, their `contentWidth` goes to 0, which both maps already tolerate (`containerWidth > 0 ? … : 3.4`) and re-derive from on open. Below 1024 px the fold must not exist at all: `.maps-fold, .maps-row { display: contents }` dissolves both wrappers so the maps are again direct children of `.charts-grid` and therefore lanes 4 and 5 of the carousel. `e2e/mapas-plegados.spec.ts` pins both halves. ⚠️ **Its mobile assertion was decorative on the first try and the negative control caught it**: comparing a map's *width* against the grid's passes either way, because two maps stacked inside one lane are still a full lane wide. What distinguishes the cases is *position* — as lanes they share a `y` and sit a lane apart in `x`; stacked they share `x`. ⚠️ And the three boxes must be measured **in one `page.evaluate`**: `switchTab()` fires a smooth scroll, so three separate `boundingBox()` calls land at different points of the animation and report a 170 px `y` gap on a perfectly correct layout.
- **Inside the fold the two maps are `repeat(2, 1fr)` — half the row each.** The old 1:2 split was a consequence of sharing a grid with the donuts, not a property of the maps; alone in their own row, equal halves is the answer, and the deviation map goes from ~425 to ~650 px, which is where its block headers stop fighting for space. ⚠️ Check both of the look-through map's thresholds before touching this width: `isNarrow` at 460 px (below it the rectangles show only the percentage and the names move to the ranking) and `viewH` at 560 (below it the canvas gets taller). At ~650 both are clear, which is why halving the lane costs nothing visible. `e2e/mapa-desviacion.spec.ts` pins the equal split, and that test **used to assert the opposite** — it was rewritten with its reason rather than deleted, because a contract change has to be visible in the test that guarded it.
- **Anything that needs the maps visible in an e2e spec must call `abrirMapas()` first** (`e2e/util/cartera.ts`). Folded they are in the DOM with no box, so `toBeVisible()` and `boundingBox()` both fail on a map that is built correctly — a timeout that points at the assertion instead of at the fold. The helper is a no-op on mobile, where the header is not drawn.
- **The onboarding tour is two runs, not one** (`OnboardingTour.svelte`, driver.js). Which one fires is decided by `portfolio.hasAnyHoldings`: an **empty** portfolio gets three steps whose only job is getting data in (manage → import CSV), and a portfolio **with holdings or in demo mode** gets six, including the tax panel. It used to be a single eleven-step run, which meant the real first-time path — "Empezar gratis" on the landing sets `bypassLanding` and enters the dashboard *empty* — explained net worth over zeros and buried "import CSV" at step 11 of 11. Relaunching from the footer after adding assets therefore upgrades you to the full run, which is the behaviour you want. `corebalance_tour_seen` is written in `onDestroyed`, **not** when the tour starts, so a reload mid-run does not burn it.
- ⚠️ **Do not add tour steps for every new feature.** The step budget is the point: a step earns its place only if the feature is something the user would not otherwise discover *exists* (that is why the tax panel has one and the maps share a single step — a map explains itself once seen). Steps without an `element` render as a centred modal, which is how the welcome step is done deliberately; the old code pointed it at `#tour-welcome`, an id that exists nowhere, and got the same result by accident.
- ⚠️ **`.tab-hidden` flips to `display: block !important` above 1024px** (there are no tabs on desktop). Any container that needs another display mode must re-assert it inside that media query — see `.sidebar-item.tab-hidden { display: flex }`. Forget it and the layout silently collapses to a single column on desktop only.
