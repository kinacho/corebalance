### Production smoke check (`scripts/prod-smoke.mjs`)

⚠️ **Everything above this line can be green while the site is down, and on 6-ago-2026 it was.** `corebalance.app` served the "Sin conexión" page to users with a perfectly good connection. Nothing was wrong with the code: the registrar's nameservers (`launch1`/`launch2.spaceship.net`) spent a few minutes signing the zone with a key that did not match the DS published in the `.app` registry, so **every** DNSSEC-validating resolver — Google, Cloudflare, Quad9, OpenDNS — returned SERVFAIL while the authoritative servers, asked directly, answered fine. To a browser that is indistinguishable from having no network: the navigation fails, and the service worker correctly serves its offline fallback. It recovered on its own about four minutes later.

Two things that class of failure teaches, and both shape the script:

- **The build can be perfect and the site unreachable.** CI checks types, tests, build and SEO against the *built* HTML; not one of those opens the public URL. A domain that doesn't resolve, a `vercel.json` rewrite that fell out, or a deploy that never got promoted all give green CI and a broken site.
- ⚠️ **Ask DNS twice — validating and not.** One failing query cannot tell "the domain doesn't exist" from "the domain exists and its DNSSEC is broken", and those have opposite fixes. If the normal query fails and the unvalidated one answers, the failure is DNSSEC and must be named as such: it is the only diagnosis that points at the registrar's panel instead of at this repo. `prod-smoke.test.ts` reproduces exactly that pair of responses and asserts the diagnosis, because getting it wrong sends the next person to read the service worker for an afternoon.
- ⚠️ **And ask more than one resolver, because that same pair of answers is also what a hiccuping validator produces.** Added 7-ago-2026. The script asked only `dns.google`, and a resolver that momentarily cannot fetch the DNSKEY returns SERVFAIL while `cd=1` still answers — **byte for byte the signature of a broken zone**. Measured that morning: two consecutive queries to Cloudflare's resolver SERVFAILed, forty samples immediately afterwards across two resolvers were clean, and a raw probe of both authoritative servers showed the zone perfectly healthy (same SOA serial, DS `28095` matching the KSK, signatures valid 30-jul → 20-ago). With one resolver that would have fired the hard `DNSSEC roto` error, prose about the registrar's panel included, for a problem that was not there. So `RESOLVERS` votes: **at least two opinions and a strict majority** before anything is declared broken, one lone dissenter is a warning, and a DoH endpoint that is down **abstains** rather than counting as a failure — that a provider is unreachable says nothing about the zone. The three (Google, Cloudflare, AdGuard) were picked by measurement, not reputation: each must serve JSON, accept `cd=1`, and actually return SERVFAIL for `dnssec-failed.org` while answering the same query with `cd=1`. Quad9 and `doh.sb` failed that bar. ⚠️ `reportaAd` exists because **AdGuard validates but never sets the AD bit**, so it votes on Status and is excluded from the "is the zone still signed" check; including it would emit a permanent, false warning.

It also covers the piece this file declares unverifiable locally: the `/offline` rewrite is Vercel's, so `vite preview` doesn't apply it, and without it Workbox cannot precache its own `offline` entry and the whole service-worker `install` fails.

- **`runSmoke()` takes both transports injected** (`get` for HTTP, `doh` for DNS) and does no I/O itself. Not purism — a broken production checker and a healthy site both read as "0 errors", which is this repo's recurring defect, so `prod-smoke.test.ts` feeds it one fixture per failure it must catch (31 cases) without waiting for the world to break. Verified by disabling the DNSSEC branch: exactly one test fails, the right one. The `doh` transport takes a `resolver` id, which is what lets a fixture answer differently per resolver and makes the majority rule testable at all. ⚠️ **All four negative controls were run, and the third one earned its keep:** removing the majority requirement fails exactly the two tests about a lone dissenter; counting an abstention as a failure fails exactly the three about unreachable endpoints; and ignoring `reportaAd` failed **nothing** — the first version of that test kept the other two resolvers healthy, so the `every` rule covered for it and it passed with the fix reverted. It now leaves the non-AD resolver as the only one answering, which is the only shape where `reportaAd` is load-bearing.
- **The offline page is recognised by `data-offline-fallback`, not by its text.** The marker proves two opposite things — that `/offline` *is* served, and that `/` and `/dashboard` are *not* serving it. It is an attribute rather than visible copy because that copy already got rewritten once: it used to say "Comprueba tu red", which sent the user to look where the problem wasn't. It now names both possibilities, since the page genuinely cannot tell them apart.
- **Deployed-version check**: the landing carries `softwareVersion` in its `SoftwareApplication` schema (from `__APP_VERSION__`, read out of `package.json`), so comparing it against the deployed commit's version is the cheapest way to catch a deploy that never shipped. The CLI retries three times, 15 s apart, because `deployment_status` fires before the CDN has necessarily invalidated the old HTML everywhere — and a guard that goes red at random gets ignored, which is worse than not having it. ⚠️ **On `schedule` runs the same mismatch is a warning, not an error** (`--version-aviso` → `versionBlanda`), and that distinction is a direct consequence of the 30-minute cron: a scheduled run landing in the two or three minutes between a release merge and the end of Vercel's build legitimately sees the previous version, and at 48 runs a day that is a false red per release. The question "did this deploy get promoted?" only makes sense to the event that accompanies a deploy, so `deployment_status` keeps the hard error. Without this, tightening the cron would have swapped one false red for another.
- **`.github/workflows/prod-smoke.yml` fires on three triggers and all three are needed.** `deployment_status` (filtered to production successes — Vercel writes that environment name both capitalised and not, so both are accepted) checks each deploy. ⚠️ **The cron is the one that would actually have caught this incident**, because the DNS broke on its own with no commit involved. ⚠️ **It was every six hours, and at that interval it did not do the job it was written for**: the 6-ago incident lasted about four minutes, so the odds of a window like that landing inside a six-hourly run are roughly 1 in 90 — the diagnosis existed, the detection did not, and the second episode was spotted by chance while checking DNS by hand. It is now `13,43 * * * *`, 48 runs a day; Actions minutes are free on a public repo and the job takes seconds because there is no `npm ci`. The minutes are 13 and 43 rather than on the hour because GitHub queues everyone's crons and the top of the hour is the most congested slot. And `workflow_dispatch` for after touching DNS or `vercel.json`. No `npm ci` in the job: the script uses only node builtins and `fetch`, so it must be able to run whatever state the repo is in.
- ⚠️ **`www.corebalance.app` is NXDOMAIN, that is an accepted state, and the check therefore says nothing about it.** The canonical is the apex, `www` appears nowhere in the repo, and the owner decided on 7-ago-2026 not to add the CNAME — so anyone typing `www` gets a browser error, and the site is fine. It used to emit a warning on every run: true, but permanent, and at 48 runs a day a warning that always fires trains you to stop reading the output, which is the exact failure mode this script exists to avoid. **Silence is the accepted baseline; the check now guards the state that would be new and genuinely broken:** `www` resolving to something that does not lead to the site. That is the hole you fall into by creating the CNAME at the registrar *before* adding the domain in Vercel — the name resolves, Vercel does not know which project owns it, and the visitor gets a certificate warning and a stranger's error page, which is *worse* than today's NXDOMAIN. So it accepts a 2xx or a redirect to the apex, warns on anything else, and warns rather than errors when the request cannot be opened at all (a missing certificate is the tell). While `www` does not exist it stays quiet; the moment it exists it starts watching.
