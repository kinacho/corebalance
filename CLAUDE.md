# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

**CoreBalance** ([corebalance.app](https://corebalance.app)) — free, local-first portfolio rebalancing calculator for passive index investors (Spanish market focus, bilingual ES/EN). Svelte 5 (runes) + SvelteKit on Vercel. User data lives in the browser (IndexedDB via Dexie); cloud sync via Firebase is optional and only for logged-in users. Market prices come from a hybrid Yahoo Finance + Financial Times backend cached in Upstash Redis.

The repo is really two apps:

- **Prerendered marketing site** — landing, blog, comparativas, herramientas, autor — under `src/routes/(public)/[[lang=locale]]/`. Spanish at `/`, English at `/en/...`.
- **The calculator** at `/dashboard` — SPA-only (`ssr = false` in its `+layout.ts`), all data client-side. Dashboard code may touch `window`/`localStorage` freely, but nothing dashboard-related may be imported into a public route.

## Architecture

### Rebalancing engine (the core math)

- `src/lib/rebalance.ts` — pure functions, no I/O: `calculatePortfolioState()` (per-position value/deviation/target, aggregates, sparkline) and `calculateRebalance()` (**cash-flow rebalancing**: buy-only, distributes a contribution pro-rata to each asset's deficit vs target; never sells, to avoid realizing capital gains). Supports `manualInterestRate` assets (cash/deposits with accrued interest).
- `src/lib/stores/portfolio.svelte.ts` — `PortfolioStore`, the app's brain (singleton `portfolio`). Holds holdings/transactions/prices/assets in `$state`, derives `ledgerHoldings` (weighted-average cost from the transaction ledger), calls `calculatePortfolioState` separately for the three buckets (`core` / `satellite` / `stocks`), handles price polling (30 s, exponential backoff, paused on hidden tab), auth, and cloud sync.
- **Non-obvious ledger accounting** (in `ledgerHoldings`): `dividend` transactions *reduce the cost basis* (they lower the average cost, they are not counted as profit); `sell` reduces total cost proportionally without changing the average cost; assets with `manualInterestRate` accrue interest per period between transactions (`rate/365 × days`). `effectiveHoldings` merges manual holdings with ledger-derived ones only for tickers with `useLedger: true`.
- Domain types in `src/lib/types.ts`; shared constants (localStorage keys, colors, tabs) in `src/lib/constants.ts`.

- ⚠️ **`src/lib/weights.ts` — the target-weight split, and it used to live inside a component.** When you drag one asset's target, the rest are redistributed **in proportion to what they already had** (which is what preserves the portfolio's relative shape), locked assets are untouched, what you ask for is clamped to what the locks leave free, and the rounding remainder is settled so the total is **exactly 1**. That last part is not cosmetic: targets that do not sum to 100 % skew every deviation the engine computes. It sat in `ManageAssets.svelte` until 7-ago-2026 and was therefore the only money arithmetic in the repo with no tests and no mutation coverage — it came out for the same reason `ledger.ts` came out of the store. The functions **never touch the store**: they return the weights and the component applies them, which is what makes them testable without a DOM. Two edges worth knowing, both pinned by tests: with every free asset at 0 (the freshly-imported CSV portfolio) it splits equally instead of multiplying by zero forever, and the rounding remainder lands on the first unlocked asset — **which can be the one you just set**, so asking for 35 % can leave you at 35,01 %.
- ⚠️ **The manage panel's button is hidden in demo mode** (`{#if !portfolio.isDemo}` in `Header.svelte`), so a browser harness cannot reach it by clicking. `scripts/verificar-pesos.mjs` opens it by dispatching the app's own `tour-step` event with `{target: 'manage'}` — a mechanism the app already has, not a test-only hook. That script is a one-off harness, not part of any suite: build first, `vite preview`, then run it. It exists because the weight split is the one piece where the unit tests prove the arithmetic and only a browser proves the wiring still reaches the store.

### Tax-aware rebalancing (Spanish IRPF) — the second engine

`calculateRebalance()` only buys. That is deliberate, but for the Spanish index investor it is *too* cautious in one very common case: **moving money between investment funds is not a taxable event** (art. 94 LIRPF, *traspaso* with tax deferral). Three pure modules cover that, all no-I/O and heavily tested:

- `src/lib/instrument-type.ts` — `resolveInstrumentType()` classifies an asset as `fund` / `etf` / `equity` / `cash` / `other`. **This is where everything else hangs from**: only `fund` can be transferred tax-free, and an ETF tracking the same index cannot. Signals in order of reliability: Yahoo's search `type` (`MUTUALFUND` is the clean one), a `0P…` ticker (how Yahoo identifies non-listed funds), the name, and lastly the ISIN — which only gives the country of issue and therefore **cannot** tell a fund from an ETF (IE00/LU covers both). Ambiguity returns `other`, and `other` is never touched by any plan. Read it through `instrumentTypeOf(asset)`, never `asset.instrumentType` directly.
- `src/lib/fiscal.ts` — FIFO over the ledger, savings-income brackets, and the wash-sale (*antiaplicación*) rule. **Deliberately diverges from `ledgerHoldings` in two ways, and both matter:** it uses FIFO (mandatory for homogeneous securities, art. 37.2) instead of weighted-average cost, and **dividends do not reduce the acquisition value here** even though they do in the ledger — fiscally a dividend is income of the year it is received. Applying the ledger's criterion would inflate the gain and the estimated tax. The wash-sale window is **2 months for listed securities and 12 months for fund units** (art. 33.5 f vs g; fund units are not admitted to trading). A blocked loss is **deferred, not forfeited** — it is still declared, it just does not offset gains this year, so it is excluded from the taxable base of the estimate.
- `src/lib/traspaso.ts` — `calculateTaxAwareRebalance()`. Pairs surplus with deficit **within each category** (targets only exist inside `core`/`satellite`/`stocks`; moving money across categories is a strategy change, not a rebalance), doing **all fund→fund pairs first** to maximise the tax-free amount. `fund → ETF` is a redemption, not a transfer: it is taxed even though the source is a fund. The savings-income scale is progressive and per-year, so tax is accumulated across the whole plan and each move pays what it adds to the scale. Also simulates how many months the contribution-only route would need, to give the user the real choice: fix it today vs fix it in N months.

Everything user-visible is labelled as an estimate, with the statutes cited in `traspaso.sources_body`. `SAVINGS_TAX_BRACKETS` / `SAVINGS_TAX_YEAR` live in **one dated constant** in `fiscal.ts` — those rates have changed three times in a decade.

### Look-through exposure and the maps

- `src/lib/lookthrough.ts` + `src/lib/data/indices.json` — what is actually inside the funds: regional and sector exposure, and overlap between positions ("your World and your S&P 500 point at the same companies"). Computed at **index level, never per holding**: real fund composition moves daily and needs a paid feed, while index weights move slowly and can be maintained by hand. Percentages are over **covered value**, not total portfolio, with `uncoveredValue` exposing what fell outside.
- **`indices.json` declares its own provenance.** Every index carries `regionsConfidence` and `sectorsConfidence`: `factsheet` (read off the official factsheet at `asOf`), `derived` (computed from other verified indices — the All-World is World + emerging), or `estimate` (order of magnitude, unverified). `calculateLookThrough()` returns `estimatedIndices` with only the unverified indices *that the user actually holds*, and the UI warns in orange. A test pins `msci-world` and `sp500` to `factsheet`. **When bumping `asOf`, re-check the factsheets and update the confidence flags** — the tests assert region and sector sums are 100 and that the World/US and S&P/tech weights match the published figures.
- `src/lib/treemap.ts` — squarified-ish treemap by binary splitting, ~30 lines, hand-rolled instead of pulling `chartjs-chart-treemap`: the maps are SVG, so they inherit `.privacy-blur` and the design tokens with no bridge, and it is deterministic and therefore testable (area conservation, no overlap, no infinite recursion on a dominant item).
- ⚠️ **The categorical palette in `constants.ts` is a validated artefact, not a taste choice.** `ASSET_COLORS` (six hues) and `CATEGORY_COLORS` (three) both pass all six checks of the `dataviz` skill's validator against the dark surface `#0d0d12`. The previous fifteen-hue palette **failed**: `#d946ef` and `#0ea5e9` sat next to each other and are indistinguishable under deuteranopia (ΔE 1.8), and eight of the fifteen were outside the lightness band. **If you touch either list, re-run the validator** (`node scripts/validate_palette.js "<hex,…>" --mode dark --surface "#0d0d12"` inside the skill). Non-obvious ordering constraints that fall out of it: green may not sit next to pink (ΔE 1.1 deutan) nor next to cyan (ΔE 11.8 even with normal vision), and blue may not sit next to violet (ΔE 0.4 deutan).
- **A seventh hue is never generated.** Past the six, charts fold the tail into an "Other" slice using `CHART_NEUTRAL`; `nextAssetColor()` reuses the least-used hue in fixed order. It used to fall back to `ASSET_COLORS[Math.floor(Math.random() * …)]`, which can hand out a colour already in the portfolio.
- ⚠️ **That rule lives in `src/lib/asset-colors.ts` now, because it was written twice and fixed once.** `AssetSearch.svelte` and `ImportModal.svelte` each carried their own `getNextColor()`; the random fallback was repaired in the first and left in the second, so **the CSV import path — the one that adds a whole portfolio at once, i.e. the only one that reliably goes past six assets — still handed out random duplicate colours.** Same shape as the FT-assets bug: one feature, several copies, broken in the copy that mattered. `assignAssetColors()` is the list version.
- ⚠️ **The demo portfolio hardcoded nine brand colours and bypassed the palette entirely** — `#00a4ef` Microsoft, `#4285f4` Google, `#555555` Apple, `#ff9900` Amazon, plus Tailwind defaults for the ETFs. Since the demo is what every first-time visitor and every screenshot sees, the example portfolio was the *worst* advertisement for the validated palette: three near-identical blues in one donut, and an asset painted the same grey as the "Otros" slice, so the chart showed two grey wedges meaning different things. It now calls `assignAssetColors()`. Two non-obvious details, both load-bearing: the assignment runs **across all three buckets at once** (per-bucket, core and stocks would both start at hue 0 and collide in the global-detail donut), and it runs in **expected-weight order, not declaration order** — the first six get the six distinct hues, and by declaration order Alphabet landed seventh, repeated IWDA's amber and the two showed up side by side.
- ⚠️ **The deviation treemap is sectioned by strategy block, and that is the fix for a whole family of colour problems — don't undo it.** **Targets are a core-portfolio concept**; satellite and stocks do not have them as such. The map used to squarify all three buckets onto one canvas and then flag two thirds of the assets as the exception ("sin objetivo") — assets that *structurally* cannot have a target. Every visual complaint it ever got came from that: first six of nine cells painted invisible, then a two-tone grey slab, then a legend carrying an entry that should not exist. None of it was a colour problem. It now squarifies **blocks by value first, then assets inside each block** (`layout` in `DeviationTreemap.svelte`; `squarify` places from the origin, so inner rects are translated into their block's slot). A block gets the diverging scale when **any of its assets has a target** (`measured`) — decided from the data, never from the block's name, so setting targets on satellites lights that block up on its own. A block without targets gets one flat hue from `BLOCK_HUES` and **no per-cell "sin objetivo" label at all**, because its header already says nobody expects a target there. The only thing still hatched is a genuine anomaly: an untargeted asset *inside* a measured block, which is the one case where a scale-less cell sits among scale cells with no gap or header between them. Two consequences of "measured is decided from the data" that were left half-done and are now handled, because the fresh-CSV portfolio (**every** asset at `targetWeight: 0`, so *nothing* is measured) is the first map most people see: the **subtitle** switches to `treemap.subtitle_no_targets`, since the usual one claims the colour is distance from target and there is no target to be distant from; and the **tooltip** has a third template, `tooltip_weight_only`, because "sin objetivo fijado" accuses the user of forgetting something that block never had. The header height is also **reserved whether or not the header is drawn** (`reservedH`, capped at a quarter of the block like the gap): subtracting it only when drawn meant a block could *shrink as the panel widened*, at the moment it crossed the "a header fits here" threshold.
- **The deviation map's midpoint is a low-chroma green, and both halves of that sentence are load-bearing.** Grey does not say "this is fine", but a saturated hue at a diverging midpoint is a genuine anti-pattern — it competes with the poles. `DEVIATION_ON_TARGET` (`#2f6b55`) is measured to sit in between: still **below the validator's categorical chroma floor** (so it reads as a near-neutral and does not compete) while being 3.2× more chromatic than the `#6b7280` it replaced. Numbers from the `dataviz` validator against `#0d0d12`, checked against what the map *actually paints* — the ramp floors, not the pure poles: normal-vision ΔE 17.7 vs the blue floor and 21.4 vs the amber, CVD 16.8 deutan / 11.8 protan. ⚠️ **The ramp still mixes from `CHART_NEUTRAL`, not from the green.** A ramp passes through its origin, and `mix(green, amber, 0.6)` is `#ac8136` — dirty olive. The small colour jump at the band edge is a feature: it marks the moment there is something to look at.
- ⚠️ **`CATEGORY_COLORS` cannot be reused inside the deviation map, however tempting.** `CATEGORY_COLORS.core` is *exactly* `DEVIATION_UNDER` and `CATEGORY_COLORS.stocks` is *exactly* `DEVIATION_OVER` — the categories donut and the deviation map already share two hex values with two unrelated meanings, in adjacent carousel lanes. So `BLOCK_HUES` is cyan / lime / violet (core / stocks / satellite), reusing only the satellite's violet. ⚠️ **It was emerald + cyan + violet and it had never been validated as a trio — emerald↔cyan is ΔE 11.8 normal-vision, the adjacency this very file declares forbidden, and a hard fail.** Not a corner case either: every asset from a CSV import is born with `targetWeight: 0`, so no block is measured and all three flat hues land on one canvas. The trio now passes all six checks all-pairs (worst: cyan↔violet ΔE 15.0 deutan, cyan↔lime 21.1 normal). **Which block gets which hue is also measured**, not arbitrary: the common case is a *measured* core, so the hues that coexist with the ramp floors are the other two, and lime is by far the best against the blue floor (31.2 normal / 29.5 protan, where cyan sat at 12.0 — a fail). Cyan therefore moves to core, which is almost never flat. Known, measured, accepted cost: violet vs the blue floor is ΔE 14.0 normal / 6.9 deutan, and lime vs the amber floor 4.3 deutan (16.8 normal, which does pass) — a failure **between different sections**, which is exactly what faceting addresses (visible gap, block header, per-cell labels) and the remedy the `dataviz` skill prescribes for all-pairs failures. Inside a single section nothing is under threshold, which is what was not true before.
- **The legend says only what the map could not say in place.** The three scale entries appear only if some block is measured; the pole swatches are **gradients** over `mix(neutral, pole, 0.6…1)`, because the map never paints the pure pole below ten points of deviation and a flat pole chip was more saturated than any cell on screen — that was a real "the legend doesn't match the map" bug. A block hue gets a legend entry **only when its header did not fit**: the conservative bucket is ~4 % of net worth, and in the narrow lane its block has no room for a header plus a cell, which used to leave an unexplained violet cell (and on mobile there is no tooltip to save it). Never both at once — a test asserts exactly that.
- ⚠️ **`text-transform` in CSS after measuring the string in JS is a bug, not a style choice.** The block headers were measured lowercase and rendered uppercase; uppercase is wider, so `approximateTextWidth` under-measured, and the `clipPath` — doing its job as the hard guarantee — cut mid-word: "ACCIONES INDIVIDUALE". The label is now uppercased in the script *before* measuring. **`letter-spacing` is the same bug one notch finer** and it survived the first fix: `.block-label` carries `letter-spacing: 0.04em`, which `approximateTextWidth` did not model, so the estimate ran ~4 % per character short. The function now takes a `letterSpacing` argument (em, like CSS) and `BLOCK_LABEL_TRACKING` mirrors the CSS value — three places that must move together, which is what the header-width test pins. General rule: CSS must not change the glyphs — **or their advance width** — after you have measured them.
- ⚠️ **SVG `<text>` neither wraps nor clips itself**, so a long label in a narrow cell paints straight over its neighbour. Two defences, and both are needed: `approximateTextWidth()` / `labelFits()` / `truncateToWidth()` decide *whether it is worth drawing* — with **per-character widths**, because a single average made all-caps tickers look 15% narrower than they render and `CASH-DEP` spilled out — and a `clipPath` per cell is the hard guarantee for when the estimate is wrong anyway. **Block headers need the same two defences**, and the test caught them missing the second: without a clip, "Cartera Conservadora" in the 4 % block paints over the block next to it. `DeviationTreemap.test.ts` asserts both invariants, on the desktop *and* the mobile geometry. ⚠️ **Two ways that header test was decorative, both fixed:** it compared each header against the widest cell in the *whole map*, so only the largest block could ever fail it; and it checked a single width, where the padding absorbs the `letter-spacing` error — it now sweeps twelve widths and asserts the label fits `blockWidth − 2 × inset`, which is what `truncateToWidth` actually promises (it fails at 360 px if the tracking is not modelled — verified by reverting the fix, not assumed). Also, **`svg.querySelector('#id rect')` does not work in these tests**: the map's clip ids are fixed per block, so a test that renders several times leaves duplicate ids in the document, the id selector resolves against the first render and then returns `null` for not being inside this SVG — a `null` that reads as "there is no clip".
- ⚠️ **Never compose a sentence by injecting another sentence into a placeholder.** `treemap.tooltip` used to take a `{target}` slot filled with either a percentage or the phrase "sin objetivo", which rendered as "**objetivo sin objetivo**". One template per case (`tooltip` / `tooltip_no_target` / `tooltip_weight_only`) instead — three, because the label that was rightly removed from the *drawing* of an unmeasured block stayed alive in `tooltipFor()` for months. The tooltip is where a retired wording hides.
- **The "Otros (N)" fold limit is one derived value, used twice.** `LookThroughMap` groups the tail of the ranking into a single slice, and how many it groups depends on whether the map is expanded (six hues' worth) or not (`MAX_CHART_SLICES - 1`). That number was written once for the fold and once for the label, so expanded the map grouped three regions and called them "Otros (4)". It is now `sliceLimit`, and the label reads `rawSlices.length - sliceLimit`.
- **The maps size their type from the container's real width, not from a media query.** A `viewBox` and an SVG `font-size` are attributes, so CSS cannot adapt them; and the deciding number is the *container* width, not the viewport — in its carousel lane a map is ~340 px **on desktop too**, which is why type tied to `matchMedia` rendered 9 px labels on a large screen. Both maps take `contentWidth` from `MapFrame` via `bind:clientWidth` and convert a target pixel size into viewBox units. In the look-through map, narrow lanes show **only the percentage** and the names are read from the ranking below, because "Consumo discrecional" truncated to "Consu…" informs nobody.
- **`MapFrame.svelte` is the shared shell of both maps**: header, subtitle, its own controls slot and the expand button. **Expanding widens the panel in place — it is not a modal.** It was one at first, and it brought every modal problem for no gain: it locked page scroll via `body.modal-open`, the lock survived closing with Escape so the page stayed frozen, and on mobile the media query that hid the expand button hid its own close button too. Widening in place has none of those states. The grid owns the width (`deviationExpanded` / `lookThroughExpanded` in `+page.svelte` flip `.map-box.is-wide { grid-column: 1 / -1 }`), because a grid item cannot leave its own track. Nothing else has to change on expand: the maps derive type size and canvas ratio from `contentWidth`, so widening the track recomputes everything. Note jsdom then needs a `ResizeObserver` — there is a stub in `src/setupTest.ts` — and tests pick a geometry by stubbing `clientWidth`, not by faking `matchMedia`.
- ⚠️ **The "no target" fill has failed twice, both times by being grey, and the deviation map now admits exactly one grey: the midpoint.** First it was white at 6 %, which over the dark surface is black — in any portfolio where only the core bucket has targets (the demo, and most real ones) six of nine cells vanished and the map looked broken. The fix was a second flat grey, and that failed differently: with six of nine cells grey the whole map read as switched off, and a second neutral also *means* the wrong thing, because it reads as "slightly more on target" when it means **not applicable**. The current answer splits the two cases, and the split is the whole point. A **whole unmeasured block** gets one flat hue from `BLOCK_HUES` and no texture at all, because its header already says nobody expects a target there. An untargeted asset **inside a measured block** — the genuine anomaly, the one case where a scale-less cell sits among scale cells with no gap or header between them — carries **hue + texture**: `UNTARGETED_FILL` (`#3b4250`, slate) with 45° stripes in `UNTARGETED_STRIPE` (`#5a6273`), so the two channels are independent and neither leans on hue discrimination. ⚠️ **This paragraph used to name `NO_TARGET_HUES` and `DARK_SURFACE`, and neither constant has ever existed in this repo** — it also had the stripe backwards, claiming it darkens toward the surface when `UNTARGETED_STRIPE` is *lighter* than its fill. Invented names in this file are worse than no names: they read as verified. `BLOCK_HUES` deliberately excludes **blue and amber** (they are the two poles, so a blue untargeted cell next to a blue "por debajo" cell is ambiguous) and **pink** (red reads as loss in a portfolio map, and pink beside green is ΔE 1.1 under deuteranopia — a forbidden adjacency of this palette). And "sin objetivo" is set apart by *italics*, not by a low alpha — white at 45 % was fine on dark grey and became illegible the moment the cells got a hue. Cells are labelled "sin objetivo" rather than showing a fabricated deviation (`deviation` is `weight − 0`, i.e. the weight again). The diverging mix starts at 60 % toward the pole, not 35 %, so a cell that has just left the band reads as coloured rather than grey. `DeviationTreemap.test.ts` asserts no fill is translucent or near-black **and resolves `url(#…)` to the pattern's own colours** — before that it read a fill it could not parse and silently passed on exactly the cells the check exists for.
- ⚠️ **Ordinary browser checks need one trick: `page.waitForURL` does not work for SvelteKit client-side navigation.** It waits for a `load` event that a client-side `goto` never fires, so it times out even though the URL changed. Poll `location.pathname` instead. Several hours were lost blaming the app for this.
- `DeviationTreemap.svelte` colours by **deviation from target, not daily change**. That is a product decision, not an oversight: daily colour teaches the user to check every day and react, which is the habit the app exists to prevent.

#### The imported portfolio can now carry its ledger, and the history window is decided by the data (10-ago-2026)

Two halves of one thing: a CSV with dates has everything needed to rebuild the past, and both the ledger and the reconstruction window were throwing it away.

- ⚠️ **Every transactional parser built a `transactions` array and dropped it.** They all raise one to feed `reduceTransactionsToPositions()` and keep only the consolidated result, so `importFromCSV` returned positions and the dates died there. Consequence: an imported portfolio is born in manual mode, **`fiscal.ts` cannot apply FIFO so the whole IRPF panel is off**, and the reconstruction cannot go backwards because `sharesAt()` does not know the past share counts and assumes today's. `ImportResult.transactions` now carries them (in the importer's own shape — `Date`, `BUY`/`SELL` — which is a different type from `$lib/types`).
- **`src/lib/importers/ledger-import.ts` decides which assets may enter with a ledger**, out of the component because it decides whether the portfolio shows the right number of shares. ⚠️ `effectiveHoldings` **prefers the ledger** over manual holdings, so an incomplete ledger means showing less than the user owns — going from *correct without history* to *with history and wrong*, which is worse because it is unnoticeable. Three conditions, and the first is the one that matters: **a sale with no purchases behind it**, which is what happens whenever somebody downloads only the last twelve months. ⚠️ Comparing the net against the position detects nothing there — the position was computed *from those same operations*, so it always ties. Also excluded: operations outside the base currency, because the ledger stores an `fxRate` per operation and the CSV does not carry the rate **of each purchase day** — writing `fxRate: 1` on a dollar asset does not leave the cost approximate, it leaves it wrong by however much the pair has moved.
- ⚠️ **`HISTORY_DAYS = 30` said "limited by what Yahoo's sparkline gives" and that was false.** `/api/prices` already asked Yahoo from 20 December of the previous year — `calculateHistoricalMetrics` needs that for YTD — so between 160 and 250 closes arrived and **all but the last 30 were discarded one line later** by a `slice(-30)`. The limit was ours. Now `diasDeHistorialPedidos()` (in `priceHelpers.ts`, because SvelteKit forbids arbitrary exports in a `+server.ts`) serves what is asked for via `?historyDays=N`, the Redis key moved to `price_history_v2:` because what is cached changed shape (full series, trimmed on the way out), and `PortfolioStore.ventanaHistorica` derives the window from **the oldest date the ledger or the edit log knows**, floored at 30 and capped at 400.
- ⚠️ **Why not just serve the long series always**: that array travels inside the prices response, which the client polls **every 30 s** — 250 points across nine assets is ~20 KB extra per response, megabytes per hour for data that does not move during a session. So it is requested once per ticker set. And ⚠️ **`this.prices = data.prices` replaces wholesale**, so without merging, the long series arrived on load and the first poll shrank it back to 30: the chart would shrink by itself thirty seconds later with no error anywhere. `performanceSeries.test.ts` pins that with two sequential `fetchPrices()`.
- ⚠️ **Widening the window without a ledger would make things worse, not better.** Past share counts come from the ledger or the edit log; with neither, `sharesAt()` returns today's for the whole past and flags it `estimated` — the very stretch that was excluded from the return figures for contaminating them. Hence the window follows the data instead of a constant.
- ⚠️ **And the fix above was incomplete: `period1` stayed anchored to 20 December of the previous year.** The output trim was widened and the *request* was not, so asking for `?historyDays=400` returned **149 points** — measured against production after deploying. The reconstruction was capped at about seven months no matter how far the ledger reached, and it looked like it worked because 149 is still far more than 30. ⚠️ **The same anchor carried a seasonal bug that had been there from the start and only shows up on one date: every 1 January the whole history collapses to two weeks**, because the anchor moves to the December just gone. Same class of defect as the one `calculateHistoricalMetrics()` takes `now` for. `period1` is now the older of the two — the 20 December anchor, needed to hold the previous year's last close for YTD, or the start of the requested window. Asking for more days bothers no calculation: the metrics search their three cutoffs inside the series, and the trim happens on the way out. `SPARKLINE_DIAS_MAX` also went 400 → **550** (≈18 months), because a 13-month ceiling should not be what truncates somebody contributing for a year and a half — the asset's own coverage should be.
- ⚠️ **The gap before the asset's price series is now filled with the shape of its index, not with a flat line.** The flat fill asserted **0 % variation** across whole months — on the case that motivated it the market moved about 10 %, so that was the error being carried. `alignPriceSeriesWithProxy()` drags the gap with `primer_precio_real × (proxy(d) / proxy(día_del_ancla))`, so the splice point matches the first real price **exactly** (no step at the join) and only the *shape* is borrowed, never the level — a proxy trading at 95 € and a fund at 12 € give the same curve. ⚠️ **`paddedBefore` deliberately does not shrink**: it is what marks the stretch as estimated, and a stretch rebuilt from an index is still an estimate — improving the number does not make it an observation. `PerformanceSeries.reconstructedWithIndexDays` counts those days so the notice can say *what* it was rebuilt from; it travels in the series and not as store `$state` because **writing state inside a `$derived` is forbidden in runes** (`state_unsafe_mutation`) — the first attempt did it and ten tests caught it at once.
- **`indices.json` gained `priceProxy` on five indices** (World, All-World, S&P 500, Emerging, World Small Cap), read through `priceProxyOf()`. ⚠️ They are **ETFs quoted in euros, not the indices**: indices publish in dollars, and dragging a euro fund with a dollar series injects the period's EUR/USD move — 5-8 % over six months, more error than the fix removes. TER and tracking difference stay inside the accepted error (0,12 % a year is 0,06 % over six months). Verified against Yahoo 10-ago-2026: all five answer in EUR with ~915 closes since 2023, well past the 550-day ceiling. An index **without** a proxy is not filled at all — the chart starts where real data starts, which beats inventing it flat. The full reasoning lives in `priceProxyNote` inside the JSON.
- **The proxies ride along in the same prices request** (`proxyTickers`), per *index* rather than per asset, so three World funds share one request and one cache entry. They are kept out of `allUserTickers` on purpose: a proxy is not a position and must not show up in the portfolio with its own weight and drift. ⚠️ **And the test that matters is the one that nearly did not exist**: four tests covered the `proxyTickers` derived value and its negative control showed **none of them noticed when the proxies stopped travelling in the request** — the derived value would stay correct, the splice would get no prices, and the chart would silently fall back to the flat fill. There is now a test on the request URL itself.
- ⚠️ **The estimated-stretch notice had gone false and there are two now.** It said "assuming you already held those shares before the app started recording changes", and with a ledger the app **does** know the share counts for each day — what it lacks is the NAV. `chart_estimated_note_index` says what the stretch was rebuilt from, because an estimate with no stated provenance is indistinguishable from data.
- **Measured, and it caps what this can ever show**: Yahoo has **229 daily closes for `0P0001XF40.F` starting 2025-08-26** against a first contribution of 2025-02-10, and 515+ for `IWDA.AS`. So depth is limited by two independent things — ledger reach *and* each asset's price series — and the second varies per asset, which `paddedBefore` already marks. Note those two tickers are the ones in `RELIABLE_FT_MAPPINGS`.
- **Verified in the browser with a real 25-lot file**: 2 assets imported, both with ledger, and the prices request carrying `historyDays`. ⚠️ **What was NOT verified on screen**: the chart itself drawing more than 30 days — the harness kept failing to reach `.history-section` behind the dashboard tabs and it was dropped rather than chased, per the rule already written here about browser rabbit holes. The mechanism is covered by unit tests instead (a 90-day-old transaction yields 91 points; a short poll does not shrink it).

### Storage

`src/lib/db/index.ts` exports the `storageProvider` singleton (`LazyStorageProvider`) which picks its backend at first use from `PUBLIC_USE_FIREBASE === 'true'` (build-time env):

- `LocalDBStorage.ts` — Dexie DB `CoreBalanceDB` (tables `userData`, `history`, `transactions`; schema versions live here). **`localDB` is `null` during SSR — always guard.**
- ⚠️ **`importAllData({ history: [] })` used to wipe all four tables and restore nothing** — restoring a backup turned into deleting the portfolio, and `SyncModal` reloads the page 1,5 s later, so the user never got to see it happen. The guard only tested `!data`. It is **not** enough that the caller validates: `validateImportData()` deliberately accepts `{ history: [] }` (pinned as correct in `utils.test.ts`), so the check has to live where the damage is done. Emptying is not a use case of that function — `deleteAccount()` is. Fixed 10-ago-2026 with `LocalDBStorage.test.ts`.
- ⚠️ **The three-layer merge in `saveUserData` (`defaults → existing → data`) is the contract of that class, not tidiness.** The store autosaves **partially**, so with `...data` before `...existing` every save would revert the fields it does not mention — contribution back to 0, holdings back to `{}` — with no error anywhere. The merge is **shallow** on purpose: `holdings` arrives whole on every save.
- **Its suite needs `fake-indexeddb`** (devDependency, zero transitive deps) because jsdom has no IndexedDB, plus `vi.mock('$app/environment', () => ({ browser: true }))` — without that, `localDB` is `null` and there is no storage to test. What the suite pins is what *decides* something: the merge order, that the `load*` methods return `[]`/`null` rather than `undefined` (the store calls `.length` on them, and the dashboard is `ssr = false`, so a `TypeError` there is a blank page), per-user isolation, and the two destructive operations. The one-line Dexie wrappers are not tested one by one — that would be testing Dexie. Note `db/index.test.ts` does **not** cover any of this: it `vi.doMock`s the module, so it tests the backend selector, not the storage.
- `FirebaseStorage.ts` — Firestore `user_data/{uid}`, `user_history/{uid}`, `user_transactions/{uid}/items/*` and `user_holding_edits/{uid}`. Sync is **last-write-wins** on `updatedAt` (and transaction conflicts are resolved by **item count** — whichever side has more wins — a fragile heuristic to keep in mind when touching sync), writes debounced 300 ms via `scheduleCloudSave()`. Firebase is code-split into its own chunk (`manualChunks` in `vite.config.ts`). Missing `VITE_FIREBASE_API_KEY` → sync silently disabled.
- `firestore.rules` (repo root) must be deployed manually; no Firebase CLI config in the repo.

### Price layer (server)

Endpoints in `src/routes/api/` — `prices`, `search`, `resolve` (ISIN→ticker), `support` (Resend email). All rate-limited via `src/lib/server/rateLimit.ts` (Redis INCR/EXPIRE, permissive in-memory fallback).

- `api/prices/priceHelpers.ts` — Yahoo bulk quotes, plus **Financial Times HTML scraping** for funds Yahoo prices badly (`RELIABLE_FT_MAPPINGS`). The FT scraper regexes HTML and silently falls back to Yahoo when FT changes markup. Subunit currencies (GBp etc.) are normalized by `correctSubunitCurrencies()`.
- ⚠️ **FT-only funds (`src/lib/ft-assets.ts`) are the second FT path, and the reason they exist is share classes, not funds.** Yahoo carries *seven* share classes of Seilern World Growth but **not** the `EUR U R` one (`IE00B2NXKW18`), and searching that ISIN returns nothing at all. That matters far more than it sounds: classes of the same fund quote at wildly different NAVs — 116,01 € the `EUR U C`, 141,67 € the `EUR U I`, 463 € the `U R` — so pricing a holding with the wrong class is not a rounding error, it values the position at a quarter of what it is. "Yahoo has the fund" is not the same as "Yahoo has what this person holds".
- ⚠️ **That feature was implemented in three places by hand and broken in the one that mattered.** `/api/search` injected the ISIN with an inline `if`, `/api/resolve` had its own copy, `priceHelpers.ts` a third in `PURE_FT_TICKERS` that nothing read, and `ft-assets.ts` — the registry meant to govern it all — was imported by nobody. Four copies of one fund, and **`/api/prices` had none**, so the ISIN went to Yahoo like any other ticker, was not found, and the asset could be searched, resolved and added to a portfolio that then could not value it. Letting someone add what the app cannot price is worse than not letting them add it. All four now read the registry, so adding a fund is again what its own docblock promised: one entry, one place. ⚠️ **No safety net:** the `RELIABLE_FT_MAPPINGS` ones fall back to Yahoo when FT changes markup; these have nothing underneath, so a broken scrape surfaces as a visible entry in `errors`. And FT's summary page carries no history, so an FT-only asset has **no sparkline and no YTD/MTD/1M** — everything value-based (weights, deviation, maps, rebalancing, tax) works, the performance surface stays blank.
- ⚠️ **`searchFtAssets()` matches by word prefix and requires *every* term**, which is not fussiness: the comparison runs the opposite way to intuition — not "does the query contain the fund name" but "does the name contain the query" — so the original `includes()` matched `ow` against "Gr**ow**th" and injected a boutique fund into unrelated searches. Only an exact ISIN query puts it at the top of the results; a name match appends, because whoever types "world" is almost always after a global index fund.
- **Measured 7-ago-2026, and deliberately not acted on:** Yahoo now prices all three `RELIABLE_FT_MAPPINGS` tickers to within 0.0–0.6 % of FT (12,265 vs 12,27 · 13,716 vs 13,72 · 5,615 vs 5,58), i.e. the premise that "Yahoo prices them badly" may no longer hold, and the app is scraping three ~90 KB pages per price request for figures Yahoo already has. ⚠️ **One snapshot at one hour is not enough to remove them**: these are unlisted funds with a single daily NAV, and the classic Yahoo failure with them is *lag* — fine at 10:00, stale at 19:00. Sample across a day before touching it.
- ⚠️ **The FT scraper never extracted YTD, and could not have.** It searched `/Year to date.*?([\d,.-]+)%/s` in `/tearsheet/summary`, but FT publishes performance on a *different URL* (`/tearsheet/performance`); measured 7-ago-2026 against the three real tearsheets the app fetches, neither "Year to date" nor "YTD" appears in any of them, and "Performance" only occurs as a tab label. So `ytd` was always `undefined` and the `+server.ts` branch reading it was dead. Removed rather than repaired: YTD already comes from Yahoo history via `calculateHistoricalMetrics()`, and rescuing it would cost one extra HTTP request per ticker for a figure the endpoint already has. Price and daily change **do** match the live markup — verified against all three mappings the same day, including the Bitcoin ETP, where FT 302-redirects `/funds/` to `/etfs/` and `fetch` follows it.
- ⚠️ **A ticker Yahoo does not return used to fail in two different ways depending on the history cache.** Cold cache: the miss path threw and the message reached the client in `errors`. Warm cache: the hit loop was `if (hit.quote) push(...)` with no `else`, so the asset **vanished from the response** — no price, no error, nothing. The user neither controls nor can observe that cache state, so the same failure was reported or hidden at random. Both paths now report it. `server.test.ts` pins it with two sequential requests (the first warms the cache), and reverting the `else` fails exactly that test while the cold-cache one stays green.
- **The parsing is separated from the fetching on purpose** (`parseFTPriceHtml` vs `fetchFTPrice`, which takes an injectable `fetchImpl`): what is fragile here is not the network, it is the regexes, and FT can recompose its page any day. The fixture in `priceHelpers.test.ts` is **real markup captured on a dated day** — kept literal, tooltips and icon `<i>` included, because the value is precisely in what nobody would invent: the daily change is loose text (`-0.02 / -0.16%`) inside two nested spans. If those tests ever fail together, check whether FT changed the page, then recapture and **re-date the capture**.
- ⚠️ **`calculateHistoricalMetrics()` takes `now` as a parameter** for the same reason `calculateTaxAwareRebalance()` does: it is date arithmetic over three cutoffs (start of year, start of month, 30 days back), and a test written against the real clock passes today and fails in January — exactly when YTD matters.
- Redis (Upstash): only the **history/sparkline** is cached (`price_history:<ticker>`, TTL 4 h); live quotes always hit Yahoo. ⚠️ **The caching lives in `src/routes/api/prices/+server.ts`, not in `src/lib/server/redis.ts`** — that file is eleven lines that build the client and export `null` when the env vars are missing. This paragraph used to point at it, which sent anyone looking for the key or the TTL to the wrong file. The per-process fallback when there is no Redis is the `historyCache` object in that same endpoint. Without `KV_REST_API_URL/TOKEN` both cache and rate limiter degrade to per-process memory — effectively no caching/limiting on Vercel serverless.
- Currency pairs (`EURUSD=X`, …) are auto-appended to every price request; `CASH-*` tickers are synthetic (1.0 EUR).

### CSV broker importers

`src/lib/importers/` — `BrokerDetector` pattern: each broker exposes `{ detect(headers) → confidence, parse(rows) }`; order in `ALL_DETECTORS` matters (DEGIRO account-statement before DEGIRO transactions, generic last). Entry points `importFromCSV()` / `importWithMapping()`; import from the `$lib/importers` barrel. `csv-utils.ts` has the delimiter/header/ISIN heuristics and auto column-mapping. Real broker CSV fixtures live in `training/` (gitignored) and are exercised by `training_csv.test.ts` (dry-run over every file) and by two cases in `parsers.test.ts`. ⚠️ **`training_csv.test.ts` pointed at `training_csv/` — a directory the history purge deleted — so from that moment it skipped every run while looking exactly as green as a suite that checks something.** Its skip-when-absent guard is still correct and necessary (a clean clone has no `training/`); what was wrong was the directory name.

- ⚠️ **`analyzeColumns()` scores each role from two independent signals — the header and the column's content — and two of its content detectors said "yes" to everything.** Both were found on 7-ago-2026 by testing the classifier the way this repo already learned to with `instrument-type`: one row per signal, so a signal that stops working cannot hide behind the other.
  - **`normalizeCurrency()` ended in `return v`**, so it never returned `null` for anything non-empty. `analyzeColumns` uses it as a *detector* (`normalizeCurrency(val) !== null`), which meant **every non-empty column of every CSV scored 0.4 for currency** — above the 0.25 threshold `suggestMappingFromAnalysis()` uses, so an arbitrary column could be auto-mapped as the currency. A detector that never says no is a broken detector. It now returns `null` for anything that is not a 3-letter ISO code or a recognised symbol/name; every caller in `parsers.ts` already ended in `|| 'EUR'`, so they get the default they wanted instead of a made-up code like `EUROS` reaching the portfolio.
  - **`looksLikeDateValue()` fell through to `Date.parse`**, and `Date.parse('10')` is a valid instant (1-oct-2001), as is `Date.parse('2026')`. So **every numeric column scored 0.5 for date**, and the shares column could be auto-mapped as the transaction date — which raises no error anywhere, it just puts the quantities in the wrong field. A bare number is now rejected before `Date.parse` sees it.
  - Both fixes were verified against the real broker CSVs in `training/`, which still pass. ⚠️ The one existing test that broke was pinning the old passthrough as intended (`'rublos'` → `'RUBLOS'`); it was rewritten with the reason, because a contract change has to be visible in the test that guarded it.
  - ⚠️ **One of the new tests was decorative and the negative control caught it**: with `25,5` in the sample only two of three values matched, the ratio stayed at 0.67 — below the 0.8 threshold — so it passed with the fix reverted. It now uses bare integers.

#### The full review of this subsystem (9-ago-2026): fifteen defects, one shape

This was the largest module in the repo that **no guard was watching** — absent from the coverage `include` and from Stryker's `mutate` — and it is the intake path of most real portfolios. Its output becomes transactions → `ledger.ts` (weighted-average cost) → `fiscal.ts` (FIFO, IRPF), so a wrong quantity, date or sign raises no error anywhere: it becomes an invented capital gain. The three files are now in the coverage ratchet; see the threshold comment in `vitest.config.ts` for why `parsers.ts` has the lowest floor in the list and why the floors were measured **with `training/` moved aside** (CI has no fixtures, and measuring on the author's machine put `parsers.ts` eleven points too high — a ratchet that would have broken on the first push).

⚠️ **They are deliberately NOT in Stryker's `mutate` yet, and the measurement is the reason.** Measured 9-ago-2026: `csv-utils.ts` **71,06 %** and `aggregator.ts` **73,03 %** (313 survivors, 13½ min for the two). `break` is 78, so adding them would fail the weekly job on the day they land — and the alternative, lowering `break`, would weaken the guard over the eight money modules to accommodate two new ones. Same reasoning as everywhere else in this file: a guard that goes red at random gets ignored, which is worse than not having it. The numbers above are the baseline for whoever raises them; note `csv-utils.ts` sits at 96,8 % statement coverage against that 71 %, which is the coverage-versus-mutation gap this file documents elsewhere, measured again.

Almost every defect had the same shape this file keeps describing: **one predicate written several times and fixed in only one copy**. Three divergent date parsers, three position consolidations, four zero-price guards.

- ⚠️ **`createSkipRow()` returns no counter, and that absence is the fix.** It used to expose `skipped` as a getter and all six parsers **destructured** it — which evaluates a getter once, capturing the initial 0 — so `ImportResult.skippedRows` was **always zero**. `ImportModal.svelte` draws its "N rows were skipped" banner and its whole per-row reason panel under `{#if importResult.skippedRows > 0}`, so that panel — translated and working — had never been shown to anyone. **This is why the other fourteen defects were invisible**: the subsystem already had the means to report them and it was disconnected. The counter and `skippedDetails` were the same state written twice; an array's length cannot be frozen by destructuring, so the counter is gone and callers use `skippedDetails.length`. ⚠️ The test that should have caught it read the counter **without destructuring** — i.e. it described the production pattern in its comment and then tested the opposite, passing green with the bug present.
- ⚠️ **`parseBrokerDate()` in `csv-utils.ts` is now the only date parsing in the subsystem, and it returns `null` instead of "today".** There were three copies: one treated *any* three-part date as day-first (so an ISO `2024-05-13` came out as day 2024 / month 5 / year 13, and its `Date.parse` fallback was unreachable for exactly the format it meant to rescue), and Trading 212, Interactive Brokers and the generic route used bare `new Date(str)`, which reads `10/01/2024` as **1 October** and returns `Invalid Date` for `15/01/2024`. Substituting today's date for an unreadable one was the other half of the defect: it invented a plausible date that shuffled the order just as well, silently. `reduceTransactionsToPositions()` sorts by date before applying average cost, so a sale processed before its purchase finds no position and is dropped — the portfolio ends up with more shares than exist. Callers now `skipRow` with `motivoFechaInvalida()`. ⚠️ **The test for this was decorative on the first attempt**: `10/01` and `15/01` still order correctly when misread, so the dates must satisfy `day1 > day2` with `month1 < month2` — 10-jan/5-feb in Europe is 1-oct/2-may in America, which reverses them.
- ⚠️ **`clasificarTipoOperacion()` picks the longest keyword match, not the first list that hits.** The buy list contained `'in'`, two letters, checked *before* the sell list with `includes`, so **`'selling'` and `'sending'` were imported as purchases**; and order-decides-ties did the same to `'koop'` inside `'verkoop'` — DEGIRO's own Dutch for buy and sell. ⚠️ Requiring a whole-word match does **not** work and was tried: `'Selling'` and `'Buying'` then match nothing and both fall through to the default, which is buy. Comparing match lengths fixes both without touching gerunds. `'dividend'` left the buy list too — it was adding shares for income rows.
- ⚠️ **The generic transactional route was reading an *amount* column as a *unit* price.** The variable was already called `priceOrTotal` and was always used as the unit price. Real case: a DEGIRO `Transacciones.csv` with an empty `Precio` column makes its parser reject the rows, the generic failsafe fires, and it maps `Valor local` — a total — as price per share: **15 shares at 1.536,67 € each**, a 23.050 € cost basis for a 2.805 € position. It now divides by the quantity when the mapped header reads as a total, which is what the MyInvestor parser already did. ⚠️ **My first fix for this was a no-op and the negative control proved it**: adding `totalTransactions` to the DEGIRO and IB detectors does nothing here, because with every row skipped that field is 0 — indistinguishable from absent. It stayed anyway for consistency with the other three parsers, but it is not what fixes this.
- **Three more silent-corruption fixes, each now pinned by a test with its negative control run:** the DEGIRO snapshot used `.set()` on a map named `accumulated`, so a repeated ISIN kept only its last row; it preferred `Valor en EUR` as the cost and labelled it `EUR`, while the store keeps `avgCost` **in the asset's currency** and multiplies by `fxRate` (see `pricesWithFx`) — converting twice and understating cost ~14 %; and its currency heuristic took the first *matching header* rather than the first candidate cell that actually holds a currency, so `Precio de` matched before `Valor local` and the `USD` next door was never seen. `parseNumber()` also lost six orders of magnitude on `1,234,567` (a `.replace(',', '.')` with no global flag) — note this is **not** the deleted single-comma thousands heuristic, which stays deleted because `1,835` really is 1,835 units.
- **`reduceTransactionsToPositions()` now returns `{ positions, warnings }`**, because it was the only place in the subsystem that could lose transactions leaving no trace: a sale with no prior position was dropped by an `if (existing)` with no `else`, and an oversell was clamped to zero in silence. That is not a rare case — it is what happens whenever someone downloads only the last twelve months.
- **`seleccionarBloque()` is shared by `importFromCSV()` and `importWithMapping()`** so they cannot pick different blocks. The manual mapping used to be built on the headers of the block chosen by detector confidence and then applied to `blocks[0]`.
- ⚠️ **`ImportModal.svelte` consolidates by resolved ticker before writing, but a second import still replaces rather than adds.** Within one file, two positions resolving to the same ticker used to overwrite each other while `importedCount` counted both. Making a *second* import additive was deliberately **not** done: it would fix "same fund at two brokers" and break something worse and more common — re-importing the same file would double the portfolio.
#### The automatic column mapping left five fields empty on a hand-made CSV (10-ago-2026)

A user's own **per-lot contribution report** — one row per purchase, with its date and its price, which is how people keep a portfolio when they keep it themselves. It imported **with no cost and no name**, and the mapping had to be corrected by hand in the modal. The root cause is one mechanism: the file brings **pairs** of similar columns, and `suggestMappingFromAnalysis` drops ties under 0.1 by returning `-1`, so every tied pair left its field blank.

- ⚠️ **`price` here means *acquisition cost*, not "what it is worth today".** `precio_medio_eur` and `valor_mercado_eur` both scored **0.80** (`valor` is in the synonym list), so `avgCost` went unmapped and **the asset entered the portfolio at cost 0** — a fabricated 100 % gain and a taxable gain on the whole market value, the exact "invented capital gain" this file keeps warning about. Market valuation is now penalised and purchase cost rewarded; rewarding alone does not work, because a tie at any distance still empties the field.
- ⚠️ **Two date columns is the one that blocks everything else.** `fecha_fiscal` (each purchase) and `fecha_valoracion` (the day the report was generated) both scored **1.00**, so `date` went unmapped and 25 operations lost their date — and with no dates there is no ledger, so the net-worth reconstruction cannot go backwards and the whole past stays flagged `estimated`. Two tiebreaks, and the second is the one that generalises because it does not depend on language or column names: **a date column with a single distinct value is not the operation date**. ⚠️ Its test had to be written against *unnamed* columns — with the `valoracion` keyword penalty in place, the header rule already rescues the real file, so a test using it passes with the variability tiebreak reverted.
- ⚠️ **A fund name ending in "Class S Acc EUR" was detected as the currency column.** `normalizeCurrency` looks for `EUR` *inside* the text (it needs to, for "Dólares USD"), so the detector said yes to a 47-character product name. The column detector now also requires the cell to be short enough to *be* a currency. Same family as the defect already documented inside that function.
- **`fondo`/`fund` were missing from the name headers**, so the fund name only scored on text ratio — tying with the `indice` column and leaving the position named after its ISIN. And a tie there is worse than elsewhere: quantity is mandatory, so `suggestMappingFromAnalysis` falls back to `shares: 0` — **the first column of the file, usually the ISIN**. Its test also had to be rewritten against an unrecognised header, for the same reason as the two above.

#### A foreign CSV was imported as DEGIRO, and there a sale *added* shares (10-ago-2026)

⚠️ **This one came out of opening the app, not of reading the code.** In the importer's preview, a CSV that buys 100 shares and sells 30 showed **600**; and a "5 at 1,20 €" dividend turned 50 shares at 105,20 € into 55 at 95,75 €. None of the three links was broken on its own:

1. the DEGIRO detector claimed any file with **ISIN + Cantidad + Precio** (`exactCount >= 3`), without requiring one single characteristic header of its own;
2. its parser derives buy/sell **from the sign of the quantity** — which is DEGIRO's real convention, sales come through negative, and therefore correct *for DEGIRO*;
3. a foreign file carries a "Tipo" column with every quantity positive, so the sign says nothing and **every sale and every dividend added shares**.

The signature this subsystem already had described, of the worst kind: `clasificarTipoOperacion()` had been fixed on 9-ago and **was never reached**. The fix is deliberately **two halves**, because either one alone leaves the hole open from the other side: the detector now demands **a signal of its own** (`Producto` or `Precio de cierre`) on top of the generic ones, and the parser reads the type column when present **in one direction only** — a declared sale never degrades to a purchase, while a declared purchase cannot contradict a negative sign — because adding shares that do not exist is the irreversible damage.

- ⚠️ **Hardening the detector is not "raise the threshold".** The real `Portfolio (1).csv` from DEGIRO **depends** on that 0,8 branch (its ISIN travels inside `Symbol/ISIN`, so it never reaches the four signals of 0,98) and it does carry `Producto`. Measured against the nine real CSVs in `training/`: all nine detect and value exactly as before.
- Visible and desirable consequence: a file like that now goes through `ColumnMapper`, which resolves it at 96 % — type column included — and asks for confirmation, instead of importing silently with the figures wrong.
- ⚠️ **What the negative control taught, and it is worth knowing before touching this:** with **one** half reverted the behaviour tests stay green, because the other half rescues them; both must be out to see them fall. That is defence in depth working rather than a decorative test, but it means whoever removes one half will not hear it from the suite.
- ⚠️ **The skip reasons are Spanish literals inside `parsers.ts`, and the panel shows them as-is in English.** They are built in pure code with no access to i18n, and nobody had seen them because until 9-ago that panel was shown to no one (see the `createSkipRow()` defect). Fixing it means turning the ~20 `skipRow` calls into a reason code plus parameters and translating in the component; still pending. The banner *was* fixed: it carried `<strong>Resumen:</strong>` **hardcoded in Spanish** in the markup, and its parenthesis listed generic causes ("headers, deposits, fees") that are not the real reasons now on display — it was written when that detail was invisible.

### i18n & routing (most convention-heavy area — read before touching)

- **typesafe-i18n**, base locale `es`. Hand-edit only `src/lib/i18n/es/index.ts` and `en/index.ts`; `i18n-types.ts`, `i18n-util*.ts`, `i18n-svelte.ts` are **generated**.
- ⚠️ **Only the base locale carries parameter type annotations.** `es` writes `{amount:string}` / `{months:number}`; `en` must write plain `{amount}` / `{months}`. Annotating the English file makes `npm run check` fail with one error per key (`Type '"…{shares:string}…"' is not assignable to type '`${string}{shares}${string}`'`). Adding keys outside `npm run dev` also means the watcher is not running, so regenerate by hand with `npx typesafe-i18n --no-watch`.
- **Single source of truth for bilingual routes:** `src/lib/i18n/bilingual-routes.js` (plain JS so `svelte.config.js` can import it). `BILINGUAL_ROUTES` feeds the prerender entries, the sitemap, hreflang alternates and the `$link()` store. `src/lib/i18n/routing.ts` is the typed wrapper (`alternates()`, `absoluteUrl`, `isLocaleCookieRoute`).
- **Blog posts are NOT bilingual routes.** Each post has its own translated slug at `/blog/<slug>` (no `/en/` prefix); the twin is resolved via frontmatter `slugs`. `src/lib/blog-locales.ts` maps slug→language with a deliberately **lazy** glob.
- **Locale resolution** (`src/hooks.server.ts`): URL prefix → post slug → `lang` cookie (only on `/dashboard` and `/api`) → `Accept-Language`. Language switching on public routes is a real `<a>` navigation with full document load — do not reintroduce store-based switching there. Two places call `setLocale`: the server hook, and the root `src/routes/+layout.ts` — which is a **universal** load, so it runs on the server too, not only in the browser.
- **`setLocale` writes a module-global store shared by every request in the process.** The hook therefore runs everything that renders components through a **single-lane queue** (`inRenderQueue`), so no other request can change the locale between `setLocale` and the response. Serializing is affordable only because that set is tiny: the 76 public pages are static files that never reach the hook, and `/dashboard` is `ssr = false`. `/api/*` is deliberately outside the queue **and never calls `setLocale`** — an endpoint that needs translations must use `i18nObject(locale)`, never the store, or it will clobber a page mid-render. `src/hooks.server.test.ts` guards this; the concurrency tests fail if the queue is removed.
- **Checklist for adding a bilingual page:** add to `BILINGUAL_ROUTES` → add `lastmod` entry to `STATIC_PAGES` in `src/routes/sitemap.xml/+server.ts` → add a `PAGES` entry in `scripts/generate-og.mjs` and `OgPageKey` in `src/lib/seo/og.ts` if it needs an OG card. A test in `src/lib/i18n/routing.test.ts` fails if `BILINGUAL_ROUTES` desyncs from the route tree.
- **In blog markdown, always write internal links with the canonical Spanish path** — the `remarkLocalizeLinks` plugin rewrites them per post language at build time.

### Styling & UI conventions

- `src/routes/layout.css` is the **only** CSS entry point (Tailwind v4 via `@import 'tailwindcss'`; there is no `tailwind.config.js`). Design tokens are CSS variables in `:root` (`--bg-primary`, `--bg-card`, `--text-primary`, `--text-muted`, `--accent-blue/green/orange`, `--state-positive/negative`, `--chart-grid/axis/ink/surface`, …).
- ⚠️ **`--accent-blue/green/orange` used to be `#3b82f6` / `#10b981` / `#f59e0b` — Tailwind's blue-500, emerald-500 and amber-500 untouched, i.e. the most recognisable default palette on the internet, and the reason the app read as generic no matter what the charts did.** They are now the same values as `CATEGORY_COLORS`, which are validated against the card surface `#0d0d12`. The split mattered because it was **semantic, not just cosmetic**: the donuts painted "Acciones" with the validated amber and `HistoryChart` painted the same category emerald green, one carousel lane apart. One hue per entity, defined once.
- Reuse the existing convention classes instead of reinventing them: `.privacy-mode`/`.privacy-blur` (blurs figures in privacy mode), `.shimmer` (skeletons), `.asset-card`, `.background-mesh`, `.noise-overlay` (uses the `#noiseFilter` SVG declared in `app.html`), `body.modal-open` (scroll lock).
- `font-variant-numeric: tabular-nums` is applied to a **closed list of classes** (`.metric-value`, `.summary-value`, `.asset-value`, `.total-value`, …) — a new class that displays figures must be added to that list or the digits jitter.
- ⚠️ **The colour of a *state* is a different layer from the colour of an *entity*, and mixing them is what made the dashboard look like six different products.** `STATE_POSITIVE` / `STATE_NEGATIVE` in `constants.ts` (mirrored as `--state-positive` / `--state-negative`) are reserved for up/down and are never a series; `ASSET_COLORS`, `CATEGORY_COLORS` and `BLOCK_HUES` are identity and never mean "good". Before this, **green meant six things at once** — acciones, money in, profit, positive return, on-target and "con DCA" — across five different greens and four different reds picked per component. The fix was subtraction: the surviving pair is two hexes that were already in the repo, and it measures **ΔE 12,0 deutan** where the worst co-occurring pair used to be 6,5. The measured cost is written in the `STATE_POSITIVE` docblock: it sits at ΔE 6,0 from `ASSET_COLORS[5]`, which is only defensible because state colour is always *text with a sign* and never a mark.
- **Chart chrome lives in `src/lib/chart-theme.ts`, chart numbers in `src/lib/chart-format.ts`.** The first holds `applyChartDefaults()`, `tooltipStyle`, `categoryAxis`, `valueAxis` and `motionAllowed()` — the three Chart.js canvases each carried their own diverged copy, and only the donut's tooltip declared the project font, so **every axis in the app rendered in the system sans**. The second is the axis/estimate number format. ⚠️ **`formatCompactCurrency()` takes the grid `step` and it is not optional decoration**: decimals are decided by the step, not the magnitude, because a portfolio moving between 116.000 € and 116.500 € otherwise writes `116k €` on all six gridlines. `stepFromTicks()` extracts it from what Chart.js hands the tick callback; `niceTicks()` does the same job for the hand-drawn SVG charts. `formatEstimate()` drops the cents — a 20-year projection quoted to the céntimo is invented precision that reads as a promise.
- **`HistoryChart` has a fourth mode, `split`: your money against what the market added.** Two stacked bands — contributed below, growth above — answering the question no net-worth chart answers: *is this going up, or have I just put more in?* The data was already in the store (`invested` / `gain`); what existed was a fifth stepped line that shipped switched off, i.e. the answer hidden behind a toggle. ⚠️ **In this mode the y axis starts at zero and that is not a preference**: with the axis starting at 60k — correct for a line, where what you read is the shape — the bands stop being proportional to what they are worth, and 64.265 € of a 116.052 € portfolio rendered as a 10 px strip under a huge slab. A stacked area whose axis misses zero is not an imprecise chart, it is a chart saying something else. Both this and the legend contradiction (the "what you put in" swatch drawing hollow because `localStorage` still had it switched off, while its band was painted) were found by **looking at the screenshot**, not by reading the code. The two fills come from `CONTRIBUTED_FILL` / `MARKET_FILL` in `chart-theme.ts`, shared with the projection cone so that past and future do not use different hues for the same idea.
- **The net-worth line is drawn green above what you contributed and red below, segment by segment** (`TREND_UP` / `TREND_DOWN` in `chart-theme.ts`) — per segment and not one colour for today's state, because that is the difference between informing and decorating: it shows *when* you were down, which a single-colour line hides. The reference depends on the mode: in euros it is the contributed capital, in return or gain it is zero, and in the stacked mode it does not apply because there the line is the edge of a band whose meaning the two fills already carry.
  - ⚠️ **They are NOT `STATE_POSITIVE`/`STATE_NEGATIVE`, and that is deliberate.** That pair's whole defence, written in its own docblock, is that it appears "in text and badges, never as the fill of a cell or an arc". A line is a mark, so the defence does not apply — and measured with the `dataviz` validator against `#0d0d12`, `STATE_POSITIVE` (#34d399) **fails the lightness band** (L 0,773, too light to paint on the dark surface). Reusing it would have been free to write and false to look at.
  - The chosen pair passes **all six checks** alongside the three `CATEGORY_COLORS` that can be drawn at the same time: green↔red ΔE **32,0** normal / **8,6** deutan; red↔the amber of "Acciones" **18,8** normal. ⚠️ The obvious candidates died there: `#dc2626` sits at **14,4**, under the hard floor of 15, and `#e11d48` drops to 5,8 deutan against the green. Green↔amber is a 7,9 protan WARN, legal only with secondary encoding — which exists, because this chart always carries a legend.
  - ⚠️ **The legend swatch had to follow**, and it did not at first: it stayed white next to a green or red line — the same legend-contradicts-chart defect as the "what you put in" band, found the same way, **by looking at the screenshot**. It now takes the colour of the last segment, i.e. today's state.
  - ⚠️ **The green cannot be `#059669`, and that took a second pass**: it is exactly `ASSET_COLORS[2]`, the emerald an asset is painted with. Reusing it would have handed the dashboard back the defect this project fixed by subtraction — "green meant six things at once" — because `CompositionBars` paints assets from that palette one row over. `#047857` is a darker step of the same family, outside `ASSET_COLORS`, and passes the six the same (worst pair: red↔green ΔE 8,4 deutan).
  - ⚠️ **And validating it turned up a pre-existing hard fail that is now fixed too: `CATEGORY_COLORS.satellite` was `#7c3aed`, ΔE 0,4 from `core` under deuteranopia.** This same file forbids blue-next-to-violet for `ASSET_COLORS`, and there it was — with both drawn as **simultaneous lines** in this chart. The donut got away with it on ordering (the amber sits between them, so adjacency holds); **a line chart has no adjacency** — series cross and share space, so the pair has to be measured all-pairs, and there it was 12,4 in normal vision, under the floor of 15. It is `#a21caf` (magenta) now: **9,7 deutan and 22,6 normal**, same purple family so the satellite is still recognisable, measured against the other two category colours *and* against the green/red of the net-worth line — the five series that can share that canvas. ⚠️ `BLOCK_HUES.satellite` deliberately **does not** change: that trio is a separate system chosen for how it coexists with the diverging ramp, and it already diverges from this one on its other two entries (cyan vs blue, lime vs amber). Measured against the ramp's blue floor, the magenta improves normal vision (14,0 → 19,9) but worsens deutan (6,9 → 3,2), so there it would be a trade rather than a fix. Here it is a fix on both.
- ⚠️ **`HistoryChart` drew its line with `tension: 0.45`, and a spline does not interpolate — it overshoots.** On a net-worth chart that is peaks and troughs of money that never existed, drawn by the curve engine rather than by the data. It is `0` now, in all three line charts. Related and deliberate: an inflow is a **filled** dot and an outflow a **hollow** one — same hue, shape carries the difference — because the outflow used to be painted amber next to a tooltip footer written expressly to say *a sale is not a loss*. Its ranges are also no longer 7D/14D/30D but 1M/3M/YTD/1A/Todo defaulting to **Todo**: a maximum horizon of one month says the same thing this file elsewhere forbids the deviation map from saying.
#### The two return figures did not match the chart they sit next to (10-ago-2026)

Four defects behind one complaint — *«no casan el gráfico de evolución del patrimonio con lo del coste del timing»*. All four were arithmetic or labelling, none was visible in a screenshot; they came out of reading `performance.ts` against `HistoryChart.svelte` and then **running the pure modules to get numbers**.

- ⚠️ **The two returns included the *estimated* days.** `reconstructDailySeries` flags `estimated: true` the days it cannot really see and fills them with an estimate; the chart honours that — draws them differently and warns — while `twrPeriod`/`mwrPeriod` folded them into the arithmetic in silence. Measured: with two estimated days at the front, the period TWR went from a real **2,00 %** to **13,33 %** — eleven points of invented return, in the figure the UI presents as "what your assets returned". They now start at `firstMeasuredIndex`, which **already existed and already had tests**: what was missing was anyone reading it. A fully estimated window returns `0`/`null` so the panel switches off instead of inventing a figure, and `TimingCost.svelte` now decides `hasFlows` over the measured stretch too — a contribution landing in the estimated days can no longer enable a comparison that does not include it.
- ⚠️ **TWR and MWR dated the flows one day apart, and their difference is the headline.** `twrIndex()` counts an inflow at the **start** of its day (`base = begin + inflow`); `moneyWeightedReturn()` placed it at `i / span`, the **close**. So the two metrics measured different exposures and the gap the UI calls "the cost of your timing" carried a residue that was not timing. Not negligible: with `[1000, 2000 (+1000), 1800]` — contribute, then eat the whole following drop, no calendar decision to judge — it produced an MWR *worse* than the TWR, i.e. a fabricated penalty. `flowTime()` aligns them, and both give −10 %. ⚠️ **The test that covered this was passing on floating-point noise**: with the convention aligned its assertion (`mwr < twr`) survives on a bisection error of **−3,2e−13**. It was rewritten with the shape where timing genuinely exists — money in after a good stretch and before a bad one — which measures **−5,57 pp**, and gained a mirror case (**+6,42 pp** for contributing after a fall) plus a test that pins the convention itself.
- ⚠️ **`YTD` and `Todo` never warned that they show a month, and `Todo` is the default range.** The series cannot exceed `HISTORY_DAYS` (30) because the reconstruction lives off Yahoo's sparkline, and `overlaySnapshots` is a `points.map()` — it fills gaps inside the window, it does not lengthen it. So every saved snapshot older than a month is unreachable, and the old predicate (`days !== null && points.length < days`) skipped exactly the two ranges whose `days` is `null`. The decision now lives in **`src/lib/history/range.ts`**, out of the component, for the usual reason: it decides something. It distinguishes two situations that were being conflated — `short` ("you haven't been here that long", nothing is missing) from `capped` (there *is* older history the reconstruction cannot reach), because `short`'s wording asserts there is no more data and in the second case there is. `PerformanceSeries.oldestKnownDate` carries the fact the chart cannot know on its own. ⚠️ A range of N days is **today plus the N−1 before it** (what the `slice` draws), so `rangeStartDate` subtracts `days - 1`: with `- days` the requested date falls one day behind a full window and «1M» would warn *always* — a permanent warning, which this file elsewhere calls the failure mode to avoid. Its own test caught that.
- ⚠️ **`timing_period_note` said «Cifras del periodo mostrado» and that was false.** The figures are computed over the whole series while the chart slices to the selected range *and* rebases the TWR to its first visible day (`twrBase`). Measured on one series: **−4,05 %** in the panel against **−3,73 %** and **−1,79 %** for windows starting at day 10 and 20. With today's ranges that divergence is only reachable via `YTD` in January — narrow, but the sentence was wrong the moment you touched the selector. The note now declares the days it actually measured, which after the first fix matches no selector range by design.
- **What was checked and is *not* a defect**, kept because the next reader will suspect it too: the `Math.max(0, …)` in `investedSeries()` does not misattribute contributed capital to the market — the case built to force the clamp never triggers it, and the scenario that seemed to show it had impossible inputs (5.000 € of value on 400 € of cost). And `moneyWeightedReturn`'s `hasInflow || hasOutflow` guard is dead code rather than a bug: the opening value and the closing value always enter as flows, so both are always true, but `TimingCost.svelte` gates on its own `netFlow` check before any of it reaches the screen.
- **`TimingCost.test.ts` exists for the same reason as `TaxAwareRebalance.test.ts`**: verified in `vite preview` that the demo portfolio has no contributions or sales, so in a browser this panel *always* says «hace falta al menos una aportación», and the populated path was exercised nowhere. `performance.ts` and `range.ts` are both in the coverage ratchet now (94/90 and 100/95) — being outside it is how a figure the user reads as their own drifted eleven points.
- ⚠️ **`Projections.svelte` draws a scenario cone, and the single deterministic line it replaced was the politest lie in the app.** It said "in twenty years you will have 702.854,19 €" when it meant "if you hit 7 % on each of 240 consecutive months, this is what falls out". No year returns its mean. `src/lib/montecarlo.ts` runs a seeded Monte Carlo (600 paths) and returns p10/p25/p50/p75/p90 per year; the seed is fixed for the same reason `calculateTaxAwareRebalance()` takes `now` — without it there is no test, and a chart that reshapes itself when you move an unrelated slider reads as broken. ⚠️ **`annualReturn` is the MEDIAN, not the arithmetic mean**, which is what makes the central line compound at exactly the rate the slider says; a property test pins it. Volatility is a **visible control, not a hidden constant**, because the width of the cone is the user's assumption exactly as much as the return is, and burying it would be selling an invented figure as data again. On the dark ground the *more* probable ribbon is the *lighter* one — the comment in the markup said the opposite until the render was actually looked at.
- **`Projections.svelte` previously drew an SVG stacked area, not 21 CSS bars.** The bars stacked `invested` *above* `profit` (first child of a `flex-direction: column` is the top one), had no axis, legend or tooltip, and used translucent fills — the exact thing `DeviationTreemap.test.ts` has a test to forbid. The two fills are **two steps of one blue** rather than two hues, because contributed capital and growth are parts of one total, not competing categories; the dark step is at 2,89:1 against the surface, under 3:1, which is why the legend carries labels and the three figures are stated in full above the chart.
- Font: Plus Jakarta Sans, **self-hosted** in `static/fonts/` with woff2 400/700 preloads.
- **The heavy visual effects were measured and are not a performance problem — don't "optimize" them away.** `.background-mesh` (`filter: blur(80px)`, 40px on mobile, plus a 25 s infinite `transform` animation), the full-viewport `.noise-overlay` (`feTurbulence`) and the card `backdrop-filter: blur()` were all suspected of hurting LCP and INP. `npm run measure:filters` on throttled mobile says otherwise: LCP sits around 600–700 ms — roughly a third of the 2.5 s "good" threshold — and **every** difference between having the effects and removing them came out smaller than the run-to-run noise floor, sometimes with the wrong sign. The animation costs nothing sustained either: median frame 16.7 ms and **zero** frames over 32 ms in every variant, because a `transform` animation on a filtered layer is composited. These are lab numbers; the deciding data would be real Speed Insights field metrics, which need the Vercel account.
- Dashboard tabs (`src/routes/dashboard/+page.svelte`): all tabs render **always** and are hidden with `class:tab-hidden` — deliberately no `{#if}` per tab, so Chart.js canvases don't remount and lose state. Don't "optimize" this into conditionals. Same applies to the two maps, whose region/sector toggle would reset on every tab change.
- ⚠️ **Two of the three donuts are gone, and the reason is that they were doing no work.** "Estrategia actual" and "Detalle Global" were the same assets with a different denominator, and past four slices nobody reads 13,02 % against 10,98 % off two arcs — they read it off the legend, which means the legend was the chart and the ring was decoration. Worse, the legend *couldn't* do the job either: `iShares Core MSCI World` and `iShares Core MSCI EM IMI` share an 18-character prefix, so both truncated to `iShares Core MS…` with **no `title`, no ticker and no tooltip** — two legend rows saying literally the same thing, and that is the normal case for the target user (iShares Core / Vanguard FTSE / Amundi Prime all pair like that). `CompositionBars.svelte` replaces both: ranked bars grouped by block, full names, and room for the thing a donut structurally cannot show — **the target**. Grid went from five lanes to four.
- **`src/lib/drift.ts` + `DriftChart.svelte` answer the one question no competitor answers: _how long have you been out of band?_** The deviation map answers it for today; this answers it for the last months, which is also the only way to see whether the rebalances you did actually achieved anything. Ghostfolio and Portfolio Performance show what you hold and what it returned — neither shows how long you have been off-target, because neither is a rebalancing tool. ⚠️ **Drift is measured inside the block, never over net worth**: targets are weights within `core`, so individual stocks rallying does not unbalance an 80/10/10 — it only makes core weigh less overall. Measuring over the total would invent a deviation every time an untargeted block moves; a test pins exactly that. Two more things it needs: `DailyPoint.byTicker` (the reconstruction already computed per-asset values and threw them away — the change is additive and the field is optional, because snapshot-derived points genuinely have no breakdown and a gap is more honest than a zero), and `driftAxisMax()`, which ⚠️ **must never scale below the band**: a perfectly on-target portfolio peaks at 0,2 pp, so scaling to the data would push a ±5 band off both ends of the canvas and draw the calmest possible portfolio as the most alarming one.
- ⚠️ **`isWithinBand()` exists because the exact edge of the band was decided by the sign of the rounding error.** A holding at 15 % against a 20 % target computes `0,15 − 0,2 = −5,000000000000002` pp and a bare `<=` calls it out of band, while the mirror case (`0,85 − 0,8` → 4,999999999999993) calls it in. Found by the boundary test in `drift.test.ts`; both modules now ask the same shared function, so they cannot answer differently.
- **`src/lib/composition.ts` is the pure half of that panel**, same split as `weights.ts` and `treemap.ts`. It carries `TOLERANCE_BAND_PP` — 5 points, the figure the project's own blog post already uses, **absolute not relative**: a 10 % target with a 5 pp band tolerates 5–15 %, not 9,5–10,5 %. ⚠️ `compositionScaleMax()` must consider the *targets* and not just the bars, because a heavily underweight asset puts its marker beyond every bar — and ⚠️ **the demo portfolio does not exercise that**: its worst case is covered by the 8 % headroom, so the first version of that test passed with the fix reverted. The test now uses a 40 %-actual-vs-80 %-target fixture. `CompositionBars.test.ts` covers the wiring the pure tests cannot see (a tick and a band only on rows that have a target, band wrapping the marker, nothing escaping the track).
- **The bar is the asset's colour; the state lives in position and in the number.** Whether you are inside the band is read from where the bar ends relative to the band rectangle, plus a signed figure in `pp` wearing the state colour and an arrow. Painting the bar amber would say "this asset is amber" and "this asset is high" with one channel.
- **`.charts-grid` was five lanes: three donuts and the two maps** (now four — see above). On mobile it is a scroll-snap carousel (`repeat(5, 100%)`), on desktop a fixed three-column grid — fixed columns rather than `auto-fit` precisely so that spans are predictable. **The look-through map used to span two of those three lanes, and that rule is gone**: it existed because the maps shared the grid with the donuts, where a single 400 px lane left a dead third column, and it stopped applying the moment the maps moved into their own folded row (see below). ⚠️ It is worth remembering how it failed before, because the same trap is still open for any span: the CSS comment and this file both claimed the rule for months while nothing implemented it. Whatever sets a span must also carry `:not(.is-wide)` — expanding sets `grid-column: 1 / -1` on the same property and has to win. Widening a map's lane also un-narrows the map itself, which is what turns on the region names inside its rectangles, since everything there derives from `contentWidth`. The maps live here rather than in a section of their own because as full-width cards they took two screenfuls of mobile scrolling; as carousel lanes they are two more swipes. Two consequences to keep in mind when adding a lane: every lane needs `align-self: start`, or the tallest one (the look-through map) stretches the donuts into a huge empty box; and that same map's footnotes are inside a `<details>`, and its mobile canvas is deliberately *not* square, for the same reason.
- ⚠️ **On desktop that grid is no longer three equal columns and the maps are no longer lanes of it — they are folded behind one line.** The complaint that started it was "too many charts in a row", and measuring four mockups said the height was not really the problem: deleting two panels only took ~13 % off, because a panel promoted to full width costs back most of what deleting its neighbour saved. What made the tab read as a wall was that **five panels carried exactly the same visual weight**, inside a glass card that was itself inside a glass card, under a third one for the history chart. So: `.charts-row-card` and `.history-section` drop their background, border, shadow and `backdrop-filter` above 1024 px (they keep them on mobile, where the frame is what gives the carousel lane an edge), the history chart is the one thing at full width, and composition / categories / drift share **one** row. The measured result on the same mockup was **−45 % of height**, the largest of the four options and the only one that deletes nothing.
- ⚠️ **The three lanes are `1.25fr 0.8fr 1.15fr` and the uneven split is load-bearing.** With three equal thirds the composition panel gets ~370 px and truncates fund names to `iShares Core MSCI W…` — which is the exact defect that killed the two donuts, reintroduced one layout later. At `1.25fr` it gets ~465 px on a 1440 px viewport and the names fit. Known and accepted cost: with a nine-asset portfolio the composition list runs ~420 px tall against ~200 for the donut, so the row's bottom edge is ragged. `align-self: start` stays (stretching would turn the two short lanes into huge empty boxes, which is the older lesson above).
- ⚠️ **The maps fold with CSS, never with `{#if}`, and `display: contents` is what keeps mobile intact.** `.maps-fold` wraps both maps plus the header button; folded, `.maps-fold:not(.is-open) .maps-row` is `display: none`, so the two panels **stay mounted** — unmounting would reset the look-through map's region/sector toggle, the same reason the tabs never use conditionals. Hidden, their `contentWidth` goes to 0, which both maps already tolerate (`containerWidth > 0 ? … : 3.4`) and re-derive from on open. Below 1024 px the fold must not exist at all: `.maps-fold, .maps-row { display: contents }` dissolves both wrappers so the maps are again direct children of `.charts-grid` and therefore lanes 4 and 5 of the carousel. `e2e/mapas-plegados.spec.ts` pins both halves. ⚠️ **Its mobile assertion was decorative on the first try and the negative control caught it**: comparing a map's *width* against the grid's passes either way, because two maps stacked inside one lane are still a full lane wide. What distinguishes the cases is *position* — as lanes they share a `y` and sit a lane apart in `x`; stacked they share `x`. ⚠️ And the three boxes must be measured **in one `page.evaluate`**: `switchTab()` fires a smooth scroll, so three separate `boundingBox()` calls land at different points of the animation and report a 170 px `y` gap on a perfectly correct layout.
- **Inside the fold the two maps are `repeat(2, 1fr)` — half the row each.** The old 1:2 split was a consequence of sharing a grid with the donuts, not a property of the maps; alone in their own row, equal halves is the answer, and the deviation map goes from ~425 to ~650 px, which is where its block headers stop fighting for space. ⚠️ Check both of the look-through map's thresholds before touching this width: `isNarrow` at 460 px (below it the rectangles show only the percentage and the names move to the ranking) and `viewH` at 560 (below it the canvas gets taller). At ~650 both are clear, which is why halving the lane costs nothing visible. `e2e/mapa-desviacion.spec.ts` pins the equal split, and that test **used to assert the opposite** — it was rewritten with its reason rather than deleted, because a contract change has to be visible in the test that guarded it.
- **Anything that needs the maps visible in an e2e spec must call `abrirMapas()` first** (`e2e/util/cartera.ts`). Folded they are in the DOM with no box, so `toBeVisible()` and `boundingBox()` both fail on a map that is built correctly — a timeout that points at the assertion instead of at the fold. The helper is a no-op on mobile, where the header is not drawn.
- **The onboarding tour is two runs, not one** (`OnboardingTour.svelte`, driver.js). Which one fires is decided by `portfolio.hasAnyHoldings`: an **empty** portfolio gets three steps whose only job is getting data in (manage → import CSV), and a portfolio **with holdings or in demo mode** gets six, including the tax panel. It used to be a single eleven-step run, which meant the real first-time path — "Empezar gratis" on the landing sets `bypassLanding` and enters the dashboard *empty* — explained net worth over zeros and buried "import CSV" at step 11 of 11. Relaunching from the footer after adding assets therefore upgrades you to the full run, which is the behaviour you want. `corebalance_tour_seen` is written in `onDestroyed`, **not** when the tour starts, so a reload mid-run does not burn it.
- ⚠️ **Do not add tour steps for every new feature.** The step budget is the point: a step earns its place only if the feature is something the user would not otherwise discover *exists* (that is why the tax panel has one and the maps share a single step — a map explains itself once seen). Steps without an `element` render as a centred modal, which is how the welcome step is done deliberately; the old code pointed it at `#tour-welcome`, an id that exists nowhere, and got the same result by accident.
- ⚠️ **`.tab-hidden` flips to `display: block !important` above 1024px** (there are no tabs on desktop). Any container that needs another display mode must re-assert it inside that media query — see `.sidebar-item.tab-hidden { display: flex }`. Forget it and the layout silently collapses to a single column on desktop only.

### hooks.server.ts

Does five things: locale resolution, `lang` cookie policy (`Vary: Cookie` only on `/dashboard`/`/api` so public pages stay CDN-cacheable), security headers, a hand-built CSP, and the `X-Robots-Tag` for `/dashboard`. **Any new third-party script/domain must be added to `cspDirectives` there.**

#### The three soft 404s Search Console was reporting (10-ago-2026)

Reported for `/dashboard` and `/en/herramientas`. Three unrelated causes, all measured against production before touching anything.

- ⚠️ **The service worker only registered at the root and on first-level routes, and that is a PWA bug that has nothing to do with SEO.** Read off the compiled bundle: the virtual module emits `new Workbox('./sw.js', { scope: './' })` — **relative**, so it resolves against the page's directory. `/en/herramientas` requests `/en/sw.js` and `/blog/importar-csv-degiro` requests `/blog/sw.js`; both 404 (verified: `/sw.js` is 200, `/en/sw.js` is 404). Only `/` and one-level routes ever worked, because their directory *is* the root. Measured by rendering production in Chromium: two console errors on all 35 English URLs, the 24 blog posts, the four tools and the individual comparisons; **zero on `/`**. So precache, offline mode and `beforeinstallprompt` only existed for someone who entered through the home page — not for someone arriving at a post from Google, which is the normal case. Fixed with `base: '/'` + `scope: '/'` in the `SvelteKitPWA` options (note the `scope: '/'` at line ~237 is the *manifest's*, a different thing). Third time this file records a silent PWA failure that left the impression of being solved.
- ⚠️ **`/dashboard` redirects to the landing page in JavaScript, which is the textbook soft 404.** Not just "an empty shell": with `ssr = false` a crawler gets the `app.html` skeleton, and then the gatekeeper's `goto('/')` fires because there is no session — measured in `vite preview`, where requesting `/dashboard` ends up rendering the landing (6.542 chars of `<main>`, headings like "Por qué creé CoreBalance"). Google's own guidance names redirecting-to-home instead of returning 404 as a soft 404. ⚠️ **And `robots.txt` no longer blocks it, which is the counter-intuitive half of the fix**: a `Disallow`ed URL is never crawled, so the crawler never sees any `noindex` and its status in the report **can never change**. Blocking saves crawl budget; it does not deindex. The `noindex` therefore travels as an HTTP header from `hooks.server.ts` — not as the `<meta>` in `dashboard/+page.svelte`, which on an `ssr = false` page only exists after hydration. `hooks.server.test.ts` pins the header, its absence on the five public routes, **and that `robots.txt` does not re-block `/dashboard`** — because if someone puts that `Disallow` back, the header silently stops being readable and no other test would notice.
- **`/en/herramientas` was the thinnest page on the site**: 2.026 characters of `<main>`, much of it the nav and footer repeated across all 70 URLs. Technically flawless — English title and h1, self-referencing canonical, `lang="en"`, reciprocal hreflang — so thin content was the only structural explanation left. ⚠️ **The JS error above cannot be the cause on its own**, and saying so matters: the same error was on `/blog/importar-csv-degiro`, which has 1.512 words and indexes fine. Fixed with real content rather than filler — a four-step "what order to use them in" and four FAQs that deliberately do not repeat the cards or the "why free" note — taking it to **4.700 characters (862 words)**, plus a `FAQPage` hung off the `@graph` that already existed (one JSON-LD block per URL; two would compete). The FAQ is marked up only because it is visible in the HTML.
- **`static/offline.html` now declares `noindex`**, because it is served with 200 at both `/offline` and `/offline.html` and its content says something went wrong — the definition of a soft 404. It is deliberately **not** added to `robots.txt`, for the same reason as `/dashboard`.
- ⚠️ **Known and untouched**: with four tools in a three-column grid, the fourth card sits alone on a second row.

## Testing

Vitest + jsdom, `*.test.ts` **colocated next to the source file**. Setup in `src/setupTest.ts` (jest-dom, `matchMedia`/`scrollTo` polyfills). The SvelteKit plugin is loaded, so `$lib`/`$app` aliases work in tests. Component tests use `@testing-library/svelte`. Key suites: `rebalance.test.ts` (core math), `fiscal.test.ts` + `traspaso.test.ts` + `instrument-type.test.ts` (the tax engine — where being wrong costs the user money, so FIFO, the progressive scale, the wash-sale windows and "a fund→ETF move is not a transfer" all have their own cases), `lookthrough.test.ts` (also the integrity of `indices.json`: sums, confidence flags, no undeclared region/sector keys), `treemap.test.ts` (area conservation and no overlap), `importers/parsers.test.ts` (all broker detectors), `importers/training_csv.test.ts` (real CSVs from `training/`, skipped when there are no fixtures — as an `it.skip`, so the report tells "skipped" apart from "checked nine files", which a green `expect(true).toBe(true)` did not; and a fixture that parses to **zero positions now fails**, since a detector quietly matching nothing is the failure mode that matters here), `stores/ledgerHoldings.test.ts` (the ledger's accounting **through the store**, not colocated with `portfolio.svelte.ts` — which is why a file-based "what has no test" count misses it: it looks like the suite of a `ledgerHoldings.ts` that does not exist. It pins the documented rules — weighted-average cost, a sell that reduces total cost without moving the average, dividends that lower the cost basis — plus fees on buys *added* and on dividends *subtracted*, `avgCost` in the asset's currency against `totalCostBase` in the base one, and interest accruing on each period's balance rather than the final one. `Date.now()` is mocked in every accrual test: it is date arithmetic, so a test on the real clock passes today and fails in three months), `i18n/routing.test.ts`, `i18n/version.test.ts` (guards the copies of the version number listed in Gotchas — note `package-lock.json` carries a sixth copy that this test does **not** cover, and it had drifted to 1.9.0), and `scripts/seo-audit.test.ts` (runs the SEO linter against a deliberately broken mini-build in `scripts/__fixtures__/seo-audit/` — a linter that stops detecting looks exactly like a clean site, so it needs its own fixture). `vitest.config.ts` therefore includes both `src/**` and `scripts/**`.

Tests must use **fixed dates**, never `Date.now()` — the fiscal windows are date arithmetic and a suite that passes today would fail in three months. `calculateTaxAwareRebalance()` takes `now` in its options for exactly that reason.

`TaxAwareRebalance.test.ts` renders the component with a mocked store, and it exists for a specific reason: **the demo portfolio is exactly on target**, so in a browser that panel always says "nothing to move" and the populated path was never exercised anywhere.

### The four mechanical guards (Layer 0)

They exist because the recurring defect in this repo is not a wrong algorithm, it is **a check that cannot fail**: one adversarial review turned up three of them at once (a suite pointing at a directory that no longer existed and therefore skipped every run, an `expect(true).toBe(true)` standing in for "no fixtures", and a width assertion measured against the widest cell in the whole map, so only one cell of nine could ever fail it). Each guard answers a different question, and none replaces another — that is the point of having four.

- **`scripts/doc-drift.mjs` — does the prose still name real code?** Every backticked identifier and path in `CLAUDE.md` must exist. Caught nothing today because it is what would have caught `NO_TARGET_HUES` / `DARK_SURFACE`. ⚠️ Two design details it cannot live without: `MENCIONES_HISTORICAS` (an allowlist **with a written reason per entry** — this file legitimately cites things that were deleted or never existed), and the fact that identifiers are searched in **code only, never in `.md`** — with markdown in the haystack the audited document validated its own claims, which the fixture caught. Its first version reported 53 orphans out of 53 (it compared `fs.existsSync` against `fiscal.ts`, `/dashboard`, `--accent-blue/green/orange`…); a guard with 53 false positives does not get fixed, it gets silenced.
- **`scripts/test-quality.mjs` — is there an assertion at all?** Flags literal tautologies and tests with no `expect`. Two false positives it had to learn: comments are stripped (it was accusing the very comment that documented a fix) and so are template literals (a test whose *string* contains `it(...)` split the parser and hid its own assertions). `it.skip` is legitimate and exempt.
- **Per-file coverage thresholds (`vitest.config.ts`) — did the line even run?** A short explicit list, with floors set to the measured value rounded down, so the ratchet can only tighten. No global percentage: an 80 % across 147 files says nothing about any of them. It started as the pure money modules and gained the price layer on 7-ago-2026 (`priceHelpers.ts` and the `prices` endpoint): they are not pure, but they fail more expensively and far more quietly — a wrong price raises no error anywhere, it becomes a wrong deviation and ends up as wrong rebalancing advice. ⚠️ Note the list is `include` **and** `thresholds`: a file named only in `thresholds` is never instrumented and the floor silently guards nothing.
- ⚠️ **A surviving mutant is not automatically a missing test — but assume it is until you have proved otherwise, because "equivalent" is the comfortable answer.** Investigated properly on 7-ago-2026 for the 66 survivors of `lookthrough`/`treemap`, by **applying each mutant by hand and diffing the function's output** over a set of inputs: if no input distinguishes it, no test can kill it. Of the fifteen studied, nine were real gaps and six are genuinely equivalent, each for a nameable reason — and ⚠️ **three of my first four "equivalent" verdicts were wrong**, overturned only by designing an input that could tell the difference. The probe is the cheap part; designing an input that *can* fail is the whole job.
  - **Real gaps, now killed:** the sort of items by size in `squarify` (nothing pinned the order — area conservation, no-overlap, containment and determinism all hold with the order broken), the split point of `place`, and the ordering of `calculateLookThrough`'s overlaps. ⚠️ The overlap-order test that already existed **could not kill its own mutants**: its positions produced a naturally descending order, so removing the `sort` changed nothing. The shape that works is two tiny positions first and two huge ones after — pairs are generated `i<j`, so the last pair is the biggest and the natural order is ascending.
  - ⚠️ **Pinning the split point needed the *shape* of a rectangle, not a count or an area.** Moving the cut by one element still leaves three items per side and still conserves area, because the split is proportional either way; what changes is how each half subdivides — 150×66,7 for the first rect with the correct cut, 100×100 with `>=`, 75×133,3 with the sign flipped. Two assertions were written and discarded before that, each verified against the mutants rather than assumed.
  - **Equivalent, with the reason:** `total <= 0` in `place` is unreachable (`squarify` filters `value > 0` before calling it); the `split >= items.length` cap is unreachable (at the last index `accumulated + value === total > total / 2`, so the loop always breaks first); and the `sharedA === null || sharedB === null` guard is **redundant, not unreachable** — `null` coerces to 0, so a null share yields `duplicatedValue === 0` and the `<= 0` check two lines below already drops it, and both variables are always assigned together so `&&` ≡ `||`. The `estimatedIndices` cluster is unreachable *given the data*: no index in `indices.json` is currently flagged `estimate`.
- **`stryker.config.json` — would the test notice if the behaviour changed?** The only one that answers that, and the only one coverage cannot fake (a test with no assertions scores 100 % coverage). ⚠️ **Stryker is deliberately not a dependency**: its tree carries a `qs` advisory that `npm audit fix` does not resolve, and a permanent Dependabot alert on a public repo is a bad trade for a weekly tool. It runs through `npx` (`npm run test:mutation`, or the weekly `.github/workflows/mutation.yml`); ~16 min for the six modules. **`break` is 78 against a measured aggregate of 81.39 %** (6-ago-2026, up from 70.39 that same morning) — same ratchet rule as the coverage floors: the measured value with a couple of points of slack for mutant flakiness, so it can only tighten.
  **First measurement, 6-ago-2026, and it is the most useful number the guards produced:** coverage 90–97 % against a mutation score of 62–80 % — `rebalance.ts` **61.92 %** (89 survivors) with 97.19 % statement coverage, `traspaso.ts` 66.14 %, `instrument-type.ts` 68.13 %, `fiscal.ts` 75.26 %, `treemap.ts` 76.98 %, `lookthrough.ts` 79.66 %. That gap *is* the difference between "the line ran" and "a test would notice if the behaviour changed".
  **The three worst were then worked through, and the pattern repeated in all three** (6-ago-2026): `rebalance.ts` 61.92 → **89.36 %**, `traspaso.ts` 66.14 → **81.35 %**, `instrument-type.ts` 68.13 → **82.97 %**. Two lessons that generalise to the modules still untouched:
  - **The report tells you which tests were decorative.** In `traspaso.ts` the anti-wash-sale test could not kill the mutants of the very line it was written for, because it asserted `netRealizedGain` — computed *outside* that condition. What the condition decides is whether the loss enters the progressive scale, which is only visible with a gain to offset. Same shape in `rebalance.ts`: three tests for the contribution split, all landing on `factor = 1`, so the branch that pro-rates — the normal one in a real portfolio — was never exercised.
  - **Deduplication kills mutants without writing tests.** The same mutant surviving in two places means one predicate written twice: `rebalance.ts` had the allocation math duplicated across both branches (+7.4 points from extracting `asignacionDe()`), and `traspaso.ts` had "is this amount worth moving?" written five times (+4.2 points from `meritaMover()`). **Look for repeats in the report before writing a single test.**
  - For a classifier, the answer is a table with one row per signal: `instrument-type.ts` had 50 survivors that were almost all "one alternative of a `||` never exercised alone" — `ty === 'FUND'`, the `-USD` suffix and the `INDEXA` check could each be **deleted** without a test noticing.
  Coverage moved with it: `rebalance.ts` and `instrument-type.ts` are now at 100 % statements, `traspaso.ts` at 98.2, and the per-file ratchets were tightened to match.
  ⚠️ Two settings that are not optional: **`tsconfigFile: ""`** (Stryker's tsconfig preprocessor cannot resolve modules when run through `npx`, and the tests go through vite anyway, so it has nothing to contribute) and **`ignorePatterns`** for `node_modules/.vite` and the build dirs — without it Windows dies with `EPERM: rmdir` on the sandbox's vite cache. CI runs on Ubuntu, where that class of failure does not happen, so the weekly job is the authoritative measurement.

### What is deliberately not unit-tested, and why

⚠️ **The big components carry no unit tests, and that is a decision rather than a backlog item.** `dashboard/+page.svelte` (1.023 lines), `LedgerModal.svelte` (890), `AssetCard.svelte` (856), `Header.svelte` (843) and what remains of `ManageAssets.svelte` (~1.380) are layout, wiring and presentation. Rendering assertions over them cost a lot per hour and mostly re-state the markup; what they could actually break — the dashboard not booting, the map not drawing, the tax panel showing nothing — is already covered by `e2e/`, which exercises the real thing.

The line that decides what gets a unit test is not "is it big" but **"does it decide something?"**. When a component turns out to be deciding, the answer is to take that piece *out* of the component, not to test the component: that is what happened to the target-weight split on 7-ago-2026 (`weights.ts`) and to the ledger before it (`ledger.ts`). Three component suites exist (`DeviationTreemap`, `HeroSummary`, `TaxAwareRebalance`) and each has a specific reason to — the last one because the demo portfolio is exactly on target, so the populated path of that panel is never exercised in a browser.

If someone later adds real logic to one of these files, the fix is the extraction, not a rendering test.

### E2E (`e2e/`, `playwright.config.ts`)

Runs against `vite preview`, so **`npm run build` first**; the service worker, the precache and hashed chunks only exist in a build. It covers what unit tests structurally cannot: that the dashboard boots at all (it is `ssr = false`, so a hydration error yields a blank page with a green build), that the service worker registers and precaches ~145 entries, the deviation map in both states, the tax panel with a real plan in it, and `/dashboard` **with the network off**.

Three things learned writing it, all of which will bite again:
- ⚠️ **Fix the locale.** `hooks.server.ts` resolves language from `Accept-Language` when there is no cookie, so the dashboard renders in English or Spanish depending on the browser; specs that assert Spanish text failed as a timeout on an empty locator, which points at the assertion and not at the cause. `use.locale` + `Accept-Language` are pinned in the config, and the map panels are located by `.map-box:not(.is-lookthrough)` rather than by their title.
- ⚠️ **Intercept `/api/prices`.** Otherwise the store overwrites the seeded prices with whatever Yahoo says, fixture tickers resolve to 0, and the positions vanish from the map by the value filter.
- ⚠️ **A service worker never controls the navigation that installs it**, so the offline specs need a second visit before anything is cached. The first version failed with "the shell was not cached" and the defect was in my expectation, not in the code.

**The offline spec earned its keep on its first run**, one day after the service-worker fix was called done: it found that the cached shell alone is useless, because on hydration SvelteKit fetches `/dashboard/__data.json` and, with that request failing, the client router lands on its own "500 Ha ocurrido un error" page. Hence the second runtime route (`corebalance-dashboard-data`). No unit test can see this: it needs a real worker and a really dead network.

### Production smoke check (`scripts/prod-smoke.mjs`)

⚠️ **Everything above this line can be green while the site is down, and on 6-ago-2026 it was.** `corebalance.app` served the "Sin conexión" page to users with a perfectly good connection. Nothing was wrong with the code: the registrar's nameservers (`launch1`/`launch2.spaceship.net`) spent a few minutes signing the zone with a key that did not match the DS published in the `.app` registry, so **every** DNSSEC-validating resolver — Google, Cloudflare, Quad9, OpenDNS — returned SERVFAIL while the authoritative servers, asked directly, answered fine. To a browser that is indistinguishable from having no network: the navigation fails, and the service worker correctly serves its offline fallback. It recovered on its own about four minutes later.

Two things that class of failure teaches, and both shape the script:

- **The build can be perfect and the site unreachable.** CI checks types, tests, build and SEO against the *built* HTML; not one of those opens the public URL. A domain that doesn't resolve, a `vercel.json` rewrite that fell out, or a deploy that never got promoted all give green CI and a broken site.
- ⚠️ **Ask DNS twice — validating and not.** One failing query cannot tell "the domain doesn't exist" from "the domain exists and its DNSSEC is broken", and those have opposite fixes. If the normal query fails and the unvalidated one answers, the failure is DNSSEC and must be named as such: it is the only diagnosis that points at the registrar's panel instead of at this repo. `prod-smoke.test.ts` reproduces exactly that pair of responses and asserts the diagnosis, because getting it wrong sends the next person to read the service worker for an afternoon.
- ⚠️ **And ask more than one resolver, because that same pair of answers is also what a hiccuping validator produces.** Added 7-ago-2026. The script asked only `dns.google`, and a resolver that momentarily cannot fetch the DNSKEY returns SERVFAIL while `cd=1` still answers — **byte for byte the signature of a broken zone**. Measured that morning: two consecutive queries to Cloudflare's resolver SERVFAILed, forty samples immediately afterwards across two resolvers were clean, and a raw probe of both authoritative servers showed the zone perfectly healthy (same SOA serial, DS `28095` matching the KSK, signatures valid 30-jul → 20-ago). With one resolver that would have fired the hard `DNSSEC roto` error, prose about the registrar's panel included, for a problem that was not there. So `RESOLVERS` votes: **at least two opinions and a strict majority** before anything is declared broken, one lone dissenter is a warning, and a DoH endpoint that is down **abstains** rather than counting as a failure — that a provider is unreachable says nothing about the zone. The three (Google, Cloudflare, AdGuard) were picked by measurement, not reputation: each must serve JSON, accept `cd=1`, and actually return SERVFAIL for `dnssec-failed.org` while answering the same query with `cd=1`. Quad9 and `doh.sb` failed that bar. ⚠️ `reportaAd` exists because **AdGuard validates but never sets the AD bit**, so it votes on Status and is excluded from the "is the zone still signed" check; including it would emit a permanent, false warning.

It also covers the piece this file declares unverifiable locally: the `/offline` rewrite is Vercel's, so `vite preview` doesn't apply it, and without it Workbox cannot precache its own `offline` entry and the whole service-worker `install` fails.

- **`runSmoke()` takes both transports injected** (`get` for HTTP, `doh` for DNS) and does no I/O itself. Not purism — a broken production checker and a healthy site both read as "0 errors", which is this repo's recurring defect, so `prod-smoke.test.ts` feeds it one fixture per failure it must catch (31 cases) without waiting for the world to break. Verified by disabling the DNSSEC branch: exactly one test fails, the right one. The `doh` transport takes a `resolver` id, which is what lets a fixture answer differently per resolver and makes the majority rule testable at all. ⚠️ **All four negative controls were run, and the third one earned its keep:** removing the majority requirement fails exactly the two tests about a lone dissenter; counting an abstention as a failure fails exactly the three about unreachable endpoints; and ignoring `reportaAd` failed **nothing** — the first version of that test kept the other two resolvers healthy, so the `every` rule covered for it and it passed with the fix reverted. It now leaves the non-AD resolver as the only one answering, which is the only shape where `reportaAd` is load-bearing.
- **The offline page is recognised by `data-offline-fallback`, not by its text.** The marker proves two opposite things — that `/offline` *is* served, and that `/` and `/dashboard` are *not* serving it. It is an attribute rather than visible copy because that copy already got rewritten once: it used to say "Comprueba tu red", which sent the user to look where the problem wasn't. It now names both possibilities, since the page genuinely cannot tell them apart.
- **Deployed-version check**: the landing carries `softwareVersion` in its `SoftwareApplication` schema (from `__APP_VERSION__`, read out of `package.json`), so comparing it against the deployed commit's version is the cheapest way to catch a deploy that never shipped. The CLI retries three times, 15 s apart, because `deployment_status` fires before the CDN has necessarily invalidated the old HTML everywhere — and a guard that goes red at random gets ignored, which is worse than not having it. ⚠️ **On `schedule` runs the same mismatch is a warning, not an error** (`--version-aviso` → `versionBlanda`), and that distinction is a direct consequence of the 30-minute cron: a scheduled run landing in the two or three minutes between a release merge and the end of Vercel's build legitimately sees the previous version, and at 48 runs a day that is a false red per release. The question "did this deploy get promoted?" only makes sense to the event that accompanies a deploy, so `deployment_status` keeps the hard error. Without this, tightening the cron would have swapped one false red for another.
- **`.github/workflows/prod-smoke.yml` fires on three triggers and all three are needed.** `deployment_status` (filtered to production successes — Vercel writes that environment name both capitalised and not, so both are accepted) checks each deploy. ⚠️ **The cron is the one that would actually have caught this incident**, because the DNS broke on its own with no commit involved. ⚠️ **It was every six hours, and at that interval it did not do the job it was written for**: the 6-ago incident lasted about four minutes, so the odds of a window like that landing inside a six-hourly run are roughly 1 in 90 — the diagnosis existed, the detection did not, and the second episode was spotted by chance while checking DNS by hand. It is now `13,43 * * * *`, 48 runs a day; Actions minutes are free on a public repo and the job takes seconds because there is no `npm ci`. The minutes are 13 and 43 rather than on the hour because GitHub queues everyone's crons and the top of the hour is the most congested slot. And `workflow_dispatch` for after touching DNS or `vercel.json`. No `npm ci` in the job: the script uses only node builtins and `fetch`, so it must be able to run whatever state the repo is in.
- ⚠️ **`www.corebalance.app` is NXDOMAIN, that is an accepted state, and the check therefore says nothing about it.** The canonical is the apex, `www` appears nowhere in the repo, and the owner decided on 7-ago-2026 not to add the CNAME — so anyone typing `www` gets a browser error, and the site is fine. It used to emit a warning on every run: true, but permanent, and at 48 runs a day a warning that always fires trains you to stop reading the output, which is the exact failure mode this script exists to avoid. **Silence is the accepted baseline; the check now guards the state that would be new and genuinely broken:** `www` resolving to something that does not lead to the site. That is the hole you fall into by creating the CNAME at the registrar *before* adding the domain in Vercel — the name resolves, Vercel does not know which project owns it, and the visitor gets a certificate warning and a stranger's error page, which is *worse* than today's NXDOMAIN. So it accepts a 2xx or a redirect to the apex, warns on anything else, and warns rather than errors when the request cannot be opened at all (a missing certificate is the tell). While `www` does not exist it stays quiet; the moment it exists it starts watching.

## Gotchas

- ⚠️ **A `.env` on the machine makes the API tests talk to real Upstash, and the flakiness only ever shows up locally.** `src/lib/server/redis.ts` builds the client whenever `KV_REST_API_URL` and `KV_REST_API_TOKEN` are set, so `checkRateLimit` skipped its in-memory fallback — the one the tests assume — and used real counters with a 60 s TTL that **survive between runs**. Measured 7-ago-2026 on `src/routes/api/search/server.test.ts`: the first three repeats pass, from the fourth they fall in cascade, and the failures go both ways — "expected 429, got 200" when a key expires mid-loop, "expected 200, got 429" when the counter arrives preloaded. CI never saw it because `ci.yml` copies `.env.example`, where those keys are empty. The fix is `vi.mock('$lib/server/redis', () => ({ redis: null }))` at the top of the suite; any new test that exercises a rate-limited endpoint needs the same line. ⚠️ Consequence worth knowing: the Redis branch of `checkRateLimit` is then exercised nowhere — it never was in CI either — and covering it means injecting the client instead of importing it.
- ⚠️ **`vi.mock('$lib/db')` does not cover the two dynamic imports the store makes, because they name different modules.** `cloudSync.test.ts` is the **only** suite in the repo that enters the cloud branch — the other three that build a `PortfolioStore` declare `isLocal: true` with a stub `onAuthStateChanged`, so they never fire the callback. Firing it exposes both: `initAuth()` imports `$lib/firebase` when the provider is not local, dragging the whole SDK through vite and calling `initializeApp` with whatever env the machine has; and `loadHistory()` imports `$lib/db/LocalDBStorage` as a fallback when the cloud returns no history — which is every test here — reaching real Dexie, where jsdom has no IndexedDB, so **every test logged a `DatabaseClosedError` to stderr that nobody read**. Both are mocked now (`localDB: null` is a state the code already guards). Measured: the first test drops **244 ms → 5 ms** and the suite's stderr noise goes from ten errors to none. ⚠️ **This was found while chasing an intermittent failure in that same suite, and it is NOT proven to be its cause** — the failure was never reproduced (seven full runs, one with every core pegged, one with `node_modules/.vite` cleared). What is proven is that the suite was talking to two real dependencies it had no business touching. If the intermittent failure comes back, the stack pointed at the `it()` line rather than at an `expect`, which is the signature of a timeout or an async error attributed to the test, not of a failed assertion.
- ⚠️ **Never rewrite a source file with PowerShell `Set-Content`.** It defaults to the system ANSI codepage, so every accented character in the file comes back mangled (`→` became `â†’` in `i18n/en/index.ts`). Half this repo is Spanish prose. Use the editing tools, or `Out-File -Encoding utf8` if there is no alternative. A `git diff --stat` that shows modified lines you did not touch is the tell.
- **`Asset.instrumentType` and `Asset.indexKey` are optional for back-compat** and filled in by `normalizeAssets()` in the store. That helper runs on **both** load paths — `loadFromStorage()` *and* the Firestore branch — because a portfolio arriving from the cloud never passes through the local one, and skipping it would leave the tax panel silent precisely for logged-in users. It only writes where there is a gap, so a manual correction from Manage Assets always wins.
- ⚠️ **`static/sw.js` used to exist as a self-unregistering stub and it has been deleted, because it did the opposite of what its own comment claimed.** The comment said "in production the PWA plugin replaces it with the real SW"; in fact `static/` is copied over the client output *after* vite-pwa writes the generated worker, so the 424-byte stub **overwrote the real 21 KB Workbox SW** at `/sw.js`. Demonstrated by removing it and rebuilding: `client/sw.js` goes from 424 bytes to 21,778 with the precache manifest intact. Production happened to serve the generated one, so the collision was luck of the adapter ordering, not design — and in a project whose PWA was already silently dead, keeping a file that can silently kill it again is the wrong trade. Killing stale workers is the real SW's job, which is what it is for. The SW is active in `vite dev` (`devOptions.enabled: true`) — hard-reload/unregister when dev looks stale.
- ⚠️ **`registerType` is `'prompt'`, not `'autoUpdate'`, and that is a data-loss fix rather than a preference.** In `autoUpdate` the virtual module listens for `controlling` and calls `location.reload()` **without asking**, so any deploy could reload the tab mid-CSV-import or mid-edit and take the work with it — in an app whose state lives in the browser, that is the deploy destroying user data. `onNeedRefresh` is never called in `autoUpdate` mode either, so there is no way to warn without changing mode. In `prompt` the new worker waits and `UpdatePrompt.svelte` lets the user decide; dismissing it does not nag, because the worker enters on its own the next time the app is opened cold. `onRegisterError` is wired too: without it a real registration failure is mute — green build, clean console, no PWA — the very silence the manual registration was added to close. Note the `.catch()` on the dynamic `import()` covers only the module failing to load, not the registration failing.
- ⚠️ **`injectRegister` is `false`, because `'auto'` shipped a `registerSW.js` that nothing ever loaded** — a 200-serving dead file that also made the PWA look registered. Registration is explicit (see below); the plugin has no reason to inject anything.
- ⚠️ **The PWA was inert in production from the start, and the reason is a silent failure worth recognising: `injectRegister: 'auto'` generates `registerSW.js` and deploys it, but never inserts the `<script>` tag that loads it** into SvelteKit's prerendered HTML. Measured before the fix: `getRegistrations()` returned **0**, zero caches, zero entries, and not one console error. So precache, offline, `autoUpdate` and the `beforeinstallprompt` that `InstallPrompt.svelte` depends on had never existed for any user — and the twenty lines of reasoning in `vite.config.ts` about `navigateFallback` described code that never ran. Registration is now explicit in `src/routes/+layout.svelte` via `virtual:pwa-register`, which does not depend on the plugin injecting anything. **The lesson generalises:** a subsystem that never runs cannot reveal its own bugs, which is why the second defect below sat undetected behind the first.
- ⚠️ **The offline fallback is precached as `offline` — no slash, no extension — and `/offline` must therefore be served.** `createManifestTransform()` in `@vite-pwa/sveltekit` rewrites every `.html` manifest entry by stripping the leading slash and the extension, so `static/offline.html` lands in the precache as `offline`. That convention assumes clean URLs are served, which is true of a prerendered SvelteKit page and false of a file in `static/`: `/offline` returned 404, Workbox could not precache the entry, and that alone would have failed the whole service-worker `install`. Fixed with a **rewrite in `vercel.json`** (`/offline` → `/offline.html`) rather than by turning the page into a route: it is deliberately self-contained — inline styles, no app JS — which is exactly what an offline fallback should be, and as a route it would drag in the bundle. ⚠️ **That rewrite is Vercel-only, so `vite preview` does not apply it and this one piece can only be verified in production.**
- Workbox deliberately does **not** precache prerendered HTML (the CDN serves it), so offline navigation needs an explicit fallback. `navigateFallback` is **`null` on purpose**: it registers a `NavigationRoute` that would serve *every* navigation from the precache, including online ones. The fallback is instead a `NetworkOnly` route with `PrecacheFallbackPlugin` pointing at `/offline` — no extension, because @vite-pwa/sveltekit rewrites `.html` manifest entries to clean URLs, which is why the old `createHandlerBoundToURL('/offline.html')` never resolved. All of it is commented in `vite.config.ts`.
- ⚠️ **`/dashboard` has its own runtime route, because one `NetworkOnly` rule for every navigation served the offline page to a user whose portfolio was already on their machine** — the exact opposite of what the app promises. It is now `NetworkFirst` (`corebalance-dashboard-shell`, 3 s network timeout, `precacheFallback: '/offline'` for the never-visited-online case), registered **before** the generic rule since Workbox matches in registration order. It is a runtime cache and not a precache entry because the shell does not exist as a file: `/dashboard` is `ssr = false` with no `prerender`, so a serverless function generates it.
- ⚠️ **The precache is an explicit list, and the brush-stroke pattern it replaced cost 281 files and 15.7 MB on a first visit.** `client/**/*.{js,css,html,ico,png,webp,woff2,svg,json,webmanifest}` swept the whole client output — 13 MB of it PNGs that only Twitter and LinkedIn ever fetch (`og/`, 28 cards; `blog/`, 42 images). Workbox's `install` is all-or-nothing, so every extra file is another chance to fail the whole worker. It is now the SPA skeleton only (JS, CSS, latin `woff2`, icons, `offline.html`, the manifest): ~135 files, ~2.4 MB. Two exclusions that matter and are invisible: `_app/version.json`, which SvelteKit fetches with `no-cache` to detect deploys and would be frozen by a precache route; and `.well-known/assetlinks.json` plus `llms*.txt`, which are for Android and crawlers, never for the app.
- `STATIC_PAGES` in the sitemap has hand-maintained `lastmod` dates — bump the date when a page's *visible content* changes (deliberately not `new Date()`).
- ⚠️ **`vercel.json` is schema-validated in strict mode: an unknown top-level key fails the build**, with `should NOT have additional property <key>`. So the usual `"//comment": [...]` trick does **not** work there — it broke a deploy. Any rationale for its contents belongs here instead. It now holds three things: `$schema` (`https://openapi.vercel.sh/vercel.json` — the only complete validation of the file, and it is a documented top-level key); `headers` for `/.well-known/assetlinks.json` (Android TWA link verification, left over from a parked Play Store deploy) and the web manifest; and the `rewrites` entry mapping `/offline` → `/offline.html`, without which the service worker cannot precache its own offline fallback (see the PWA notes above).
  **Note the environment gap that hid this:** `vite preview` resolves `/offline` on its own because `sirv` tries extensions, while Vercel's CDN does not. A path can work locally and 404 in production for that reason alone.
- ⚠️ **`github.deploymentEnabled: false` was a no-op and has been removed — and the public repo's "Production" link cannot be fixed from this repo at all.** That key does not exist: `github` accepts only `autoAlias`, `autoJobCancelation` and the legacy `silent` / `enabled`. Vercel ignores unknown *sub*-keys silently (unlike top-level ones, which fail the build), so the file looked configured and was not; verified empirically, GitHub kept receiving a Production deployment for every commit after it landed, with `environment_url` pointing at the protected immutable URL — hence the link to a Vercel login. ⚠️ **The obvious "fix" is a trap: `git.deploymentEnabled: false` is the real key and it disables automatic deploys for every branch**, i.e. the site would simply stop deploying. `src/lib/vercel-config.test.ts` now guards both the invented sub-key and that trap. The two things that would actually work are outside the repo: switch Vercel's Deployment Protection to "only preview deployments" (which makes the production deployment URL crawlable — the reason it was left on) or deploy from GitHub Actions with a token instead of the Git integration.
- Env vars: `PUBLIC_USE_FIREBASE` (build-time, selects storage backend), `VITE_FIREBASE_*`, `KV_REST_API_URL/TOKEN` (Upstash), `RESEND_API_KEY`. See `.env.example`.
- `src/app.html` contains an inline splash/gatekeeper script that **hardcodes the localStorage key `corebalance_holdings_v2`**, duplicating `STORAGE_KEY_HOLDINGS` from `src/lib/constants.ts` — renaming the key requires touching both places. It also captures `window.__deferredPrompt` (PWA install) and substitutes `%lang%` via the server hook.
- **This file is the only prose source of truth about the repo.** There used to be a parallel `.ai/` tree (61 files of rules, context and summaries) plus four root planning documents; every one of them had drifted from the code — wrong fonts, a claim that E2E tests existed, a claim that the app was "100% dynamic SSR" when it is the inverse. They were deleted rather than fixed. If you find a claim about this project in a file other than `CLAUDE.md`, `README.md` or `SECURITY.md`, distrust it and check the code.
- ⚠️ **No shebang in `scripts/*.mjs` that a test imports.** Vitest transforms them, and when Vite decides an import is CJS it hoists a shim to line 1 — landing *before* the shebang and producing `const fileURLToPath = …;#!/usr/bin/env node`, a syntax error that fails the whole test file at collection. It is **platform-dependent**: Linux (and therefore CI) resolves `node:url` as native ESM and never injects the shim, so this was green in CI and in local runs whose transform cache predated the import, then went red the moment the cache invalidated. The scripts run as `node scripts/x.mjs`, so the shebang bought nothing.
- ⚠️ **npm copies `package.json`'s indentation into `package-lock.json`**, so rewriting one with the wrong indent silently re-indents the other — a **12,000-line diff** in the file where nobody wants one. It happened twice in one session: writing `package.json` with `JSON.stringify(p, null, 2)` (the repo uses tabs) dragged the lockfile to spaces on the next install, and restoring the tabs dragged it back. Both files use **tabs** here. After any `npm install`, check `git diff --numstat -- package-lock.json`: the honest number for adding one dependency is a couple of hundred lines, not twelve thousand.
- **The version number lives in five places at once** — `package.json`, `changelog_trigger` in both i18n files, the `changelog_modal.releases` keys in both i18n files, and **two** separate lists in `ChangelogModal.svelte`: `releaseVersions` *and* `badgeColors`. They desynced once (footer stuck at v1.9.0 with the app on 1.10.0). `src/lib/i18n/version.test.ts` fails when they drift — and `badgeColors` is the one that gets forgotten, because everything renders fine without it (the badge just loses its colour), so only the test catches it. Bump all five together.
